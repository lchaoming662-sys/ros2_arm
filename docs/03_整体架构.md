# 第 03 章 整体架构

> 本章回答一个核心问题：**你在 RViz 里点一下鼠标，机械臂为什么会动？**
> 把这条链路彻底想通，你就掌握了整个 ROS 2 机械臂项目的骨架。

---

## 3.1 学习目标

读完本章你应该能够：
1. 画出 4 层架构图并说出每层的职责；
2. 完整复述"一条运动指令的旅程"（7 步）；
3. 解释三个关键设计决策：为什么 `controller_manager` 在 Gazebo 里、为什么要 `use_sim_time`、为什么仿真和真机能共用一套软件。

## 3.2 重点内容

### 3.2.1 四层架构

```
┌──────────────────────────────────────────────────────────┐
│ 第 4 层 · 人机交互     RViz 2                              │
│   显示机械臂当前姿态；让你拖动目标位姿；点 "Plan & Execute"    │
└───────────────────────────┬──────────────────────────────┘
                            │ ① 目标位姿（action: /move_action）
┌───────────────────────────▼──────────────────────────────┐
│ 第 3 层 · 运动规划     MoveIt 2（move_group 节点）           │
│   逆运动学求解 → 路径规划（避障/避自碰撞）→ 时间参数化          │
│   输出：一条关节轨迹                                        │
└───────────────────────────┬──────────────────────────────┘
                            │ ② 轨迹（action: /ros2_arm_controller/follow_joint_trajectory）
┌───────────────────────────▼──────────────────────────────┐
│ 第 2 层 · 控制        ros2_control（controller_manager）     │
│   ├─ joint_state_broadcaster     报告关节实际角度（只读）     │
│   ├─ ros2_arm_controller         跟踪轨迹，逐周期下发角度      │
│   └─ finger_controller           控制夹爪开合                │
└───────────────────────────┬──────────────────────────────┘
                            │ ③ 关节角度指令（写 command interface）
┌───────────────────────────▼──────────────────────────────┐
│ 第 1 层 · 仿真/硬件    Gazebo Fortress（ign_ros2_control 插件）│
│   物理引擎算力矩与运动；关节实际角度回写 state interface        │
└──────────────────────────────────────────────────────────┘
```

**每一层的"输入 → 输出"：**

| 层 | 输入 | 输出 | 你在哪一章实现 |
|----|------|------|--------------|
| 交互层 | 人的鼠标操作 | 目标位姿 | 第 08 章（配置 RViz） |
| 规划层 | 当前状态 + 目标位姿 | 关节轨迹 | 第 08 章（MoveIt 配置） |
| 控制层 | 关节轨迹 | 每周期关节角度 | 第 06 章（控制器 YAML） |
| 仿真层 | 关节角度 | 运动 + 实际角度 | 第 05、07 章（模型 + 世界） |

### 3.2.2 一条运动指令的完整旅程（7 步，务必背下来）

1. **你在 RViz 里拖动末端执行器**（那个彩色箭头/圆球），拖到目标位置，鼠标点 "Plan & Execute"。
2. **RViz 把目标发给 move_group**：通过 action `/move_action`，附带"用哪个规划组（arm）""目标位姿是什么"。
3. **move_group 解逆运动学**：调用运动学插件（本项目用 KDL），算出末端到达目标时各关节应该是什么角度。**如果目标根本够不到（超出臂长）或解出角度超限位，这一步就会失败**——你以后最常见的"规划失败"就发生在这里。
4. **move_group 规划路径**：用 OMPL 等规划器，从当前位置算出一条到目标的安全路径（不撞自己、不撞环境），再给路径加上时间信息，得到**关节轨迹**：每个关节在 t=0、t=0.1s、t=0.2s… 时的角度序列。
5. **轨迹通过 action 交给控制器**：`/ros2_arm_controller/follow_joint_trajectory`。这里用的就是第 01 章讲的 **action** 机制（能反馈进度、能取消）——因为一条轨迹要执行几秒钟，不是瞬时的。
6. **控制器逐周期插值下发**：`ros2_arm_controller` 每个控制周期（本项目设 100 Hz）算出"这一刻三个关节该在什么角度"，写进三个关节的 **command interface**（位置）。
7. **Gazebo 里的插件读走指令并驱动仿真**：`ign_ros2_control` 插件（跑在 Gazebo 进程内）把角度施加到虚拟机械臂上，物理引擎让它转起来；同时把关节的**实际角度**回写到 state interface，由 `joint_state_broadcaster` 广播到 `/joint_states`。MoveIt 和 RViz 订阅这个话题更新显示——**闭环完成**。

> 记忆口诀：**拖 → 解 → 规 → 发 → 插 → 驱 → 馈**。

### 3.2.3 关键设计决策一：`controller_manager` 藏在 Gazebo 进程里

新手 90% 会在这里懵。请记住：

- 你**不需要**（也不应该）单独启动一个 `controller_manager` 节点；
- 它是由 URDF 里那段 `<gazebo><plugin filename="ign_ros2_control-system">` 插件在加载时**自动创建**的，它活着就活在 Gazebo 进程内部；
- 证据：本项目实测日志里有 `Loaded system [ign_ros2_control::IgnitionROS2ControlPlugin]`，然后 `ros2 node list` 里就出现了 `/controller_manager`。

**直接推论（必须遵守的启动顺序）**：

```bash
# 终端 1 先起仿真 → 控制器随 Gazebo 一起诞生，3 个控制器自动激活
ros2 launch ros2_arm_gazebo gz_launch.py

# 终端 2 再起规划 → MoveIt 去连接已经存在的控制器
ros2 launch ros2_arm_moveit_config moveit_rviz.launch.py use_sim_time:=True
```

**顺序反了会怎样**：MoveIt（或控制器加载器）会一直打印 `waiting for service /controller_manager/list_controllers` 然后卡住不动。**那不是崩溃，是在等**。看到这句话先检查顺序，不要急着重装系统。

### 3.2.4 关键设计决策二：为什么要 `use_sim_time:=True`

仿真里的"时间"由 Gazebo 通过 `/clock` 话题广播。如果各节点各用各的真实时钟，就会出现：

- 轨迹说"第 0.5 秒到某个姿势"，控制器按真实时钟已经跑到第 1.2 秒，直接判定"轨迹太慢、超时"→ 执行失败；
- RViz 里机械臂的位姿和 Gazebo 里差一截。

**规则**：所有在仿真环境里运行、且**处理时间戳**的节点，启动时都要 `use_sim_time:=True`（`robot_state_publisher`、`move_group`、`rviz2` 都要）。

### 3.2.5 关键设计决策三：仿真与真机的对称性

注意本项目 URDF 里那行：

```xml
<xacro:ros2_arm_ros2_control name="Ros2ArmSystem" plugin_name="ign_ros2_control/IgnitionSystem"/>
```

`plugin_name` 就是"底层驱动"的插槽：
- 仿真时插 `ign_ros2_control/IgnitionSystem`（交给物理引擎）；
- 真机时插你自己写的硬件组件（把角度变成 PCA9685 的 I2C 信号）。

**上面所有软件（控制器参数、MoveIt 配置、你的节点）一行都不用改。** 这就是 ROS 2 生态的核心价值，也是 akabot 项目能"一份代码跑仿真和真机"的原因。

### 3.2.6 本项目的"通信清单"（写代码时会反复用到）

| 名称 | 类型 | 谁发 | 谁收 | 作用 |
|------|------|------|------|------|
| `/joint_states` | 话题 `sensor_msgs/JointState` | joint_state_broadcaster | RViz、MoveIt、你的监控节点 | 关节实际角度 |
| `/clock` | 话题 `rosgraph_msgs/Clock` | Gazebo（经桥接） | 所有开了 sim time 的节点 | 仿真时间 |
| `/tf`、`/tf_static` | 话题 `tf2_msgs/TFMessage` | robot_state_publisher | RViz、MoveIt | 各连杆坐标系关系 |
| `/robot_description` | 话题 `std_msgs/String` | robot_state_publisher | Gazebo 的 create 工具 | 机器人模型 XML |
| `/ros2_arm_controller/follow_joint_trajectory` | **action** | MoveIt | ros2_arm_controller | 下发轨迹 |
| `/finger_controller/gripper_cmd` | **action** | MoveIt / 你 | finger_controller | 夹爪开合 |
| `/controller_manager/load_controller` 等 | **服务** | spawner | controller_manager | 加载/启用控制器 |

## 3.3 动手实践提示

1. **验证"控制器活在 Gazebo 里"**：启动原型项目后，在终端执行
   ```bash
   ps -ef | grep "ign gazebo" | head -3     # 看 Gazebo 主进程
   ros2 node list | grep controller_manager # 它确实在
   ros2 node info /controller_manager | head -20
   ```
   把 `ros2 node info` 的输出抄进笔记，数一数它提供了多少个服务（通常十几个）。
2. **亲手验证启动顺序的重要性**：先只启动 MoveIt（不起 Gazebo），观察它是**卡住等待**还是**报错退出**；记下那句等待提示的原文。然后关掉，按正确顺序重来。
3. 用一句话（不超过 20 字）概括第 2~7 步各自的"输入→输出"，写进 `practice/notes.md`。能写得出来，第 05~08 章就不会迷路。
