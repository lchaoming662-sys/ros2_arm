|------|------|
| **① 一次只写一个文件** | 写完立刻保存、立刻验证。**不要一次抄 4 个文件再一起跑**——出错时你不知道是哪个文件的锅。 |

# 阶段一 · 让空包编译通过

> 目标：**一行功能代码都不写**，先把"骨架能编译"这件事跑通。

## 步骤 1 · 工作空间体检

### 🎯 这一步做什么

确认目录结构符合 colcon 的硬性要求，并搞清"哪些目录会被编译、哪些不会"。

### ⌨️ 执行

```bash
cd ~/ros2_arm
find src -type d | sort
```

### ✅ 立刻验证

你应当看到 3 个包目录，以及它们内部的子目录：

```
src
src/ros2_arm_bringup
src/ros2_arm_bringup/config
src/ros2_arm_bringup/launch
src/ros2_arm_description
src/ros2_arm_description/config
src/ros2_arm_description/launch
src/ros2_arm_description/rviz
src/ros2_arm_description/urdf
src/ros2_arm_gazebo
src/ros2_arm_gazebo/config
src/ros2_arm_gazebo/launch
src/ros2_arm_gazebo/worlds
```

**三条硬性约定**（违反了 colcon 就找不到你的包）：
1. 包目录必须放在 `src/` 下；
2. 每个包目录里必须有 `package.xml`；
3. `package.xml` 里的 `<name>` 要和目录名一致。

### 🔍 顺带认识一下你的工作空间

```
~/ros2_arm/
├── docs/        ← 文档。colcon 完全不理它（不在 src 里）
├── practice/    ← 你的练习区。colcon 也不理它
├── src/         ← ★ 只有这里面的包会被编译
├── build/       ← 编译中间产物（CMake 缓存、.o 文件）  ← colcon 自动生成
├── install/     ← 编好的东西（最终被 source 的就是它）   ← colcon 自动生成
└── log/         ← ★ 每个包每次编译的完整日志都在这里    ← colcon 自动生成
```

`build/` vs `install/` 的区别，记住这一句就够：**`build/` 是施工现场，`install/` 是成品仓库**。程序运行时只认 `install/`。

### 📄 要写的文件（3 个）

```
src/ros2_arm_description/package.xml
src/ros2_arm_bringup/package.xml
src/ros2_arm_gazebo/package.xml
```

> `ign_ros2_control` 和 `gz_ros2_control` 是**同一个东西的两个名字**（上游改名留下的过渡包）。两个都写上最保险，缺一个在某些版本上会报找不到。

### 🔍 代码怎么读

| 标签 | 作用 | 写错会怎样 |
|------|------|-----------|
| `<name>` | 包的唯一身份 | 与目录名不一致 → `ros2 run` 时找不到 |
| `<buildtool_depend>` | 编译工具 | 本项目的包都是 `ament_cmake`，写错直接编不过 |
| `<exec_depend>` | 运行时依赖 | 编译不受影响，但运行时 `ros2 launch` 报"包不存在" |
| `<depend>` | = `build_depend` + `exec_depend` + `build_export_depend` | 三合一简写 |
| `<export><build_type>` | 告诉 colcon "用哪种方式编" | 漏了 colcon 不知道怎么办这个包 |

**关键认知**：`package.xml` 里的依赖**不会自动安装**。它只是"声明我得靠谁"，apt 装没装是你自己的事。所以第 02 章的环境自查不能跳。

### ✅ 立刻验证

XML 语法自检（不需要 ROS，纯语法）：

```bash
for p in ros2_arm_description ros2_arm_bringup ros2_arm_gazebo; do
  python3 -c "import xml.dom.minidom,sys; xml.dom.minidom.parse('src/$p/package.xml')" \
    && echo "✅ $p/package.xml 语法 OK"
done
```

期望输出三行 `✅ ... 语法 OK`。报 `ExpatError` 就是标签没闭合或引号打错了。

### ⚠️ 坑

把 `maintainer` 改成你自己的邮箱和名字，但**千万别改 `<name>`**——它是包的身份，改了后续所有 launch/yaml 里的引用都会失效。

## 步骤 3 · 写 3 个 `CMakeLists.txt`

### 🎯 这一步做什么

告诉编译器"怎么装我的资源文件"。本项目全是**纯资源包**（只有 xacro/yaml/launch/sdf，没有 C++ 源码），所以它短得只有三行有效内容。

### 📄 要写的文件（3 个）

```
src/ros2_arm_description/CMakeLists.txt
src/ros2_arm_bringup/CMakeLists.txt
src/ros2_arm_gazebo/CMakeLists.txt
```

### ⌨️ 完整代码

**① `src/ros2_arm_description/CMakeLists.txt`**

```cmake
cmake_minimum_required(VERSION 3.8)
project(ros2_arm_description)

find_package(ament_cmake REQUIRED)

# 把资源目录安装到 install/<包名>/share/<包名>/ 下
install(
  DIRECTORY config launch rviz urdf
  DESTINATION share/${PROJECT_NAME}
)

ament_package()
```

**② `src/ros2_arm_bringup/CMakeLists.txt`**

```cmake
cmake_minimum_required(VERSION 3.8)
project(ros2_arm_bringup)

find_package(ament_cmake REQUIRED)

install(
  DIRECTORY config launch
  DESTINATION share/${PROJECT_NAME}
)

ament_package()
```

**③ `src/ros2_arm_gazebo/CMakeLists.txt`**

```cmake
cmake_minimum_required(VERSION 3.8)
project(ros2_arm_gazebo)

find_package(ament_cmake REQUIRED)

install(
  DIRECTORY config launch worlds
  DESTINATION share/${PROJECT_NAME}
)

ament_package()
```

### 🔍 代码怎么读

这 6 行里，只有 `install(DIRECTORY ...)` 是"你的内容"，其余都是固定模板：

- `cmake_minimum_required` / `project` / `ament_package()` —— 固定开头结尾，**照抄**；
- `install(DIRECTORY a b c DESTINATION share/${PROJECT_NAME})` —— 把包里的这几个**子目录**原样搬到 `install/ros2_arm_description/share/ros2_arm_description/` 下。

**为什么必须搬？** 因为 ROS 2 的运行时约定是"包的所有资源都放在 `share/<包名>/` 下"。你的 launch 文件里写 `get_package_share_directory('ros2_arm_description')`，拿到的是 `install/.../share/ros2_arm_description`，而不是你的源码目录。**不 install，运行时就是找不到文件。**

### ✅ 立刻验证

逐个核对：**`install(DIRECTORY ...)` 里列出的每个目录，都必须真实存在。**

```bash
cd ~/ros2_arm
ls -d src/ros2_arm_description/{config,launch,rviz,urdf} \
      src/ros2_arm_bringup/{config,launch} \
      src/ros2_arm_gazebo/{config,launch,worlds}
```

期望：8 行目录全部打印出来，**没有一行 `No such file`**。

### ⚠️ 坑（真实踩过，编号 B-2）

`install(DIRECTORY a b c ...)` 会**逐个检查**每个目录是否存在，**缺一个就整体编译失败**，报错长这样：

```
CMake Error at ament_cmake_symlink_install/ament_cmake_symlink_install.cmake:105 (message):
  ament_cmake_symlink_install_directory() can't find
  '/home/lichaoming/akabot-main/akabot_bringup/launch'
```

原型项目 akabot 就踩了这个——`CMakeLists.txt` 里写了 `install(DIRECTORY config launch ...)`，但仓库**漏提交了 `launch` 目录**。你的项目所有目录都已经建好了，正常不会踩到，但你要认识这个报错。

**关于空目录**：目录存在但里面是空的（比如你的 `rviz/` 现在是空的）**不会**导致失败，已实测通过。只有目录**不存在**才失败。

**两条对策**：
1. 补上目录（哪怕里面暂时空着，放一个 `.gitkeep` 占位）；
2. 或者只 install 你确实有的目录。

### 🔍 三个必知问题

**Q：`--symlink-install` 到底干了什么？**
它让 `install/` 里的文件变成**指向源码的软链接**，而不是复制。好处：改了 `.py` / `.yaml` / `.xacro` 立刻生效，**不用重新编译**。这是开发期最省时间的一个开关。

**Q：改了什么需要重新 `colcon build`？**
- 改 `package.xml` / `CMakeLists.txt` → **必编**
- **新增**文件（比如新建了 xacro） → **必编**（软链接只对已登记的文件生效）
- 改已有 `.py` / `.yaml` / `.xacro` 内容 → 不用编
- 只改了 `practice/` 里的东西 → 不用编（它不在 src 里）

**Q：怎么判断"是不是真的成功了"？**
不要看有没有 `install/` 目录——**失败时它也会被创建**。要比对包的数量：

```bash
cd ~/ros2_arm
echo "src 里有:   $(ls src | wc -l) 个包目录"
echo "install 里有: $(ls install | grep -vcE '^(setup\.|local_setup|_local_setup|COLCON_IGNORE|\.)') 个"
```

两个数字相等才算真成功。

### ⚠️ 坑（真实踩过，编号 B-1）

如果报错里出现：

```
ModuleNotFoundError: No module named 'catkin_pkg'
CMake Error: could not find PythonInterp
```

**原因**：本机装了多个 Python（系统 Python 3.10 + 某个工具链自带的 Python 3.13）。如果你的终端 PATH 被"污染"（3.13 排在前面），CMake 就会用 3.13 去找 ROS 的 Python 包，而 `catkin_pkg` 只装在 3.10 里。

**诊断**：

```bash
which python3 && python3 --version
```

如果输出的**不是** `/usr/bin/python3` 或版本不是 3.10，就是这个问题。

**对策**：用干净环境跑（冒烟测试用的就是这招）：

```bash
env -i HOME=$HOME PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
  bash -c "source /opt/ros/humble/setup.bash && cd ~/ros2_arm && colcon build --symlink-install"
```

**另一个隐藏的坑**：如果之前用"脏 PATH"编译过一次，`build/<包名>/CMakeCache.txt` 里会**缓存住那个错误的 Python 路径**，之后即使 PATH 干净了也照样报错。这时要单独删掉缓存文件：

```bash
rm ~/ros2_arm/build/*/CMakeCache.txt
```

（`--symlink-install` 模式下删缓存不会丢源码，只是下次编译慢几秒。）

> **看日志的姿势**：报错看不懂时执行
> `cat ~/ros2_arm/log/latest_build/ros2_arm_description/stdout_stderr.log | tail -40`
> 把 `<包名>` 换成报错里提到的那个包名。

## 步骤 5 · 写 `ros2_arm_core.xacro`

### 🎯 这一步做什么

定义机械臂的**全部连杆（link）和关节（joint）**。这是整个项目最长的文件（约 240 行），我把它拆成 **3 个批次**，每批都能独立验证语法。

### 📄 要写的文件

```
src/ros2_arm_description/urdf/ros2_arm_core.xacro   ← 现在还是空文件
```

### 🔍 先搞懂 3 个概念（否则代码看不懂）

| 概念 | 一句话 | 在本项目里 |
|------|--------|-----------|
| **link（连杆）** | 刚体零件，有形状、有质量 | `base_link` 底座、`link2` 大臂 |
| **joint（关节）** | 两个 link 之间的连接，决定"能不能动" | `shoulder_joint` 肩关节 |
| **xacro** | URDF 的"宏语言"，能定义变量和函数 | `box_inertia(m, x, y, z)` 算出长方体的转动惯量 |

**关节的 4 种类型**（本文件用到 3 种）：

| 类型 | 能否动 | 动的方式 | 本项目用在 |
|------|--------|---------|-----------|
| `fixed` | 不能动 | 焊死 | `world_base_joint`、`gripper_joint` |
| `revolute` | 能转，**有角度限制** | 绕某根轴旋转 | 三个机械臂关节 |
| `revolute` | 能转，**有角度限制** | 绕某根轴旋转 | 三个机械臂关节 + **两个夹爪指** |
| `continuous` | 能转，**无限位** | 无限旋转 | （本项目不用） |

#### ⌨️ 完整代码（写进 `ros2_arm_core.xacro`）

```xml
<?xml version="1.0"?>
<!-- ============================================================
     ros2_arm_core.xacro
     作用：定义机械臂的全部连杆（link）与关节（joint）
     零位：所有关节 = 0 时，机械臂竖直向上伸直
     ============================================================ -->
<robot xmlns:xacro="http://www.ros.org/wiki/xacro" name="ros2_arm">

  <!-- ================= 0. 惯量计算宏（所有连杆复用） ================= -->

  <!-- 长方体惯量：x y z 为三边长度，m 为质量 -->
  <xacro:macro name="box_inertia" params="m x y z">
    <inertial>
      <mass value="${m}"/>
      <origin xyz="0 0 0" rpy="0 0 0"/>
      <inertia ixx="${m*(y*y+z*z)/12}" ixy="0" ixz="0"
               iyy="${m*(x*x+z*z)/12}" iyz="0"
               izz="${m*(x*x+y*y)/12}"/>
    </inertial>
  </xacro:macro>

  <!-- 圆柱惯量：r 半径，h 高（轴向为 z），m 质量 -->
  <xacro:macro name="cylinder_inertia" params="m r h">
    <inertial>
      <mass value="${m}"/>
      <origin xyz="0 0 0" rpy="0 0 0"/>
      <inertia ixx="${m*(3*r*r+h*h)/12}" ixy="0" ixz="0"
               iyy="${m*(3*r*r+h*h)/12}" iyz="0"
               izz="${m*r*r/2}"/>
    </inertial>
  </xacro:macro>

  <!-- ================= 1. 颜色 ================= -->

  <xacro:property name="col_base"  value="0.55 0.55 0.58 1.0"/>
  <xacro:property name="col_arm"   value="0.90 0.45 0.10 1.0"/>
  <xacro:property name="col_joint" value="0.25 0.25 0.28 1.0"/>

  <!-- ================= 2. 尺寸与质量（要调参数只改这里） ================= -->

  <xacro:property name="base_radius"   value="0.06"/>
  <xacro:property name="base_height"   value="0.04"/>
  <xacro:property name="base_mass"     value="1.0"/>

  <xacro:property name="link1_radius"  value="0.045"/>
  <xacro:property name="link1_height"  value="0.05"/>
  <xacro:property name="link1_mass"    value="0.5"/>

  <xacro:property name="link2_width"   value="0.03"/>
  <xacro:property name="link2_length"  value="0.25"/>
  <xacro:property name="link2_mass"    value="0.4"/>

  <xacro:property name="link3_width"   value="0.025"/>
  <xacro:property name="link3_length"  value="0.22"/>
  <xacro:property name="link3_mass"    value="0.3"/>

  <xacro:property name="grip_x"        value="0.05"/>
  <xacro:property name="grip_y"        value="0.05"/>
  <xacro:property name="grip_z"        value="0.02"/>
  <xacro:property name="grip_mass"     value="0.15"/>
  <xacro:property name="finger_size"   value="0.012"/>
  <xacro:property name="finger_len"    value="0.04"/>
  <xacro:property name="finger_mass"   value="0.02"/>

</robot>
```

#### 🔍 代码怎么读

**① 惯量宏——为什么非要有它**

`<inertial>` 是"这个零件的质量分布"。仿真器靠它算重力和惯性：**每根连杆都必须有一个**，否则 Gazebo 里机械臂会直接飞出去（不是比喻，是真的会飞）。

难点在于转动惯量矩阵要填 6 个数字，手算容易错。所以用宏把公式封起来：

| 宏 | 公式 | 对应形状 |
|----|------|---------|
| `box_inertia` | `ixx = m(y²+z²)/12` 等 | 长方体 |
| `cylinder_inertia` | `izz = m·r²/2`（绕轴）, `ixx = m(3r²+h²)/12`（径向） | 圆柱 |

**参数约定**：长方体的 `x y z` 是**三边长度**；圆柱的 `r` 是半径、`h` 是高，且**轴向是 z**。这两个约定必须和后面 `<geometry>` 里的写法对上，否则算出来的惯量不是你想要的。

**② `<xacro:property>` —— 项目的"参数表"**

把所有尺寸/质量集中在一处，后面用 `${base_radius}` 引用。**好处**：调参数只改这里，不用满文件搜索。

**惯用做法**：文件名统一带前缀（`base_`、`link1_`、`grip_`），这样一眼能看出哪个参数属于哪个零件。

**③ 质量怎么估？**

本项目的质量是**工程估算**，不是实测。原则：底座最重（1.0 kg，保证稳定），越往末端越轻（0.3 kg），夹爪最轻（0.15 kg）。

**新手最容易犯的错**：给一个连杆填 `mass = 0`。仿真器会把它当成"零质量刚体"，解算直接炸。**宁可填 0.001 也不要填 0。**

### 批次 B · 底座 + 三个机械臂关节

#### 🎯 先想清楚一件事：机械臂靠什么站住？

**这是新手最容易忽略的一步。** 你只写了 `base_link`，Gazebo 里它会**自由落体**——因为它没有"被固定"的信息。

解决办法（原型 akabot 就是这么干的）：**加一个叫 `world` 的虚拟连杆，再用一个 `fixed` 关节把底座焊在世界上。**

```
world（虚拟的"地面"）──[fixed]──> base_link ──[revolute]──> link1 ──> link2 ──> link3
```

#### ⌨️ 完整代码（追加到 `</robot>` 之前）

```xml
  <!-- ================= 3. 世界链接 + 底座（把机械臂钉在地面上） ================= -->

  <link name="world"/>

  <joint name="world_base_joint" type="fixed">
    <parent link="world"/>
    <child  link="base_link"/>
  </joint>

  <link name="base_link">
    <xacro:cylinder_inertia m="${base_mass}" r="${base_radius}" h="${base_height}"/>
    <visual>
      <origin xyz="0 0 ${base_height/2}" rpy="0 0 0"/>
      <geometry>
        <cylinder radius="${base_radius}" length="${base_height}"/>
      </geometry>
      <material name="col_base"><color rgba="${col_base}"/></material>
    </visual>
    <collision>
      <origin xyz="0 0 ${base_height/2}" rpy="0 0 0"/>
      <geometry>
        <cylinder radius="${base_radius}" length="${base_height}"/>
      </geometry>
    </collision>
  </link>

  <!-- ================= 4. 关节 1：底座旋转（绕 Z 轴） ================= -->

  <joint name="base_joint" type="revolute">
    <parent link="base_link"/>
    <child  link="link1"/>
    <origin xyz="0 0 ${base_height}" rpy="0 0 0"/>
    <axis xyz="0 0 1"/>
    <limit lower="-3.14159" upper="3.14159" effort="10.0" velocity="1.5"/>
  </joint>

  <link name="link1">
    <xacro:cylinder_inertia m="${link1_mass}" r="${link1_radius}" h="${link1_height}"/>
    <visual>
      <origin xyz="0 0 ${link1_height/2}" rpy="0 0 0"/>
      <geometry>
        <cylinder radius="${link1_radius}" length="${link1_height}"/>
      </geometry>
      <material name="col_joint"><color rgba="${col_joint}"/></material>
    </visual>
    <collision>
      <origin xyz="0 0 ${link1_height/2}" rpy="0 0 0"/>
      <geometry>
        <cylinder radius="${link1_radius}" length="${link1_height}"/>
      </geometry>
    </collision>
  </link>

  <!-- ================= 5. 关节 2：肩关节（绕 Y 轴） ================= -->

  <joint name="shoulder_joint" type="revolute">
    <parent link="link1"/>
    <child  link="link2"/>
    <origin xyz="0 0 ${link1_height}" rpy="0 0 0"/>
    <axis xyz="0 1 0"/>
    <limit lower="-1.5708" upper="1.5708" effort="10.0" velocity="1.5"/>
  </joint>

  <link name="link2">
    <xacro:box_inertia m="${link2_mass}" x="${link2_width}" y="${link2_width}" z="${link2_length}"/>
    <visual>
      <origin xyz="0 0 ${link2_length/2}" rpy="0 0 0"/>
      <geometry>
        <box size="${link2_width} ${link2_width} ${link2_length}"/>
      </geometry>
      <material name="col_arm"><color rgba="${col_arm}"/></material>
    </visual>
    <collision>
      <origin xyz="0 0 ${link2_length/2}" rpy="0 0 0"/>
      <geometry>
        <box size="${link2_width} ${link2_width} ${link2_length}"/>
      </geometry>
    </collision>
  </link>

  <!-- ================= 6. 关节 3：肘关节（绕 Y 轴） ================= -->

  <joint name="elbow_joint" type="revolute">
    <parent link="link2"/>
    <child  link="link3"/>
    <origin xyz="0 0 ${link2_length}" rpy="0 0 0"/>
    <axis xyz="0 1 0"/>
    <limit lower="-2.0" upper="2.0" effort="10.0" velocity="1.5"/>
  </joint>

  <link name="link3">
    <xacro:box_inertia m="${link3_mass}" x="${link3_width}" y="${link3_width}" z="${link3_length}"/>
    <visual>
      <origin xyz="0 0 ${link3_length/2}" rpy="0 0 0"/>
      <geometry>
        <box size="${link3_width} ${link3_width} ${link3_length}"/>
      </geometry>
      <material name="col_arm"><color rgba="${col_arm}"/></material>
    </visual>
    <collision>
      <origin xyz="0 0 ${link3_length/2}" rpy="0 0 0"/>
      <geometry>
        <box size="${link3_width} ${link3_width} ${link3_length}"/>
      </geometry>
    </collision>
  </link>
```

#### 🔍 代码怎么读

**① 一个 link 有三块内容，缺任何一个都会出问题**

| 块 | 作用 | 缺了会怎样 | 谁需要它 |
|----|------|-----------|---------|
| `<inertial>` | 质量、惯量 | Gazebo 里飞天 / 报错 | **仿真**要用 |
| `<visual>` | 长什么样（给眼睛看） | RViz 里看不见 | RViz、Gazebo 显示 |
| `<collision>` | 碰撞体（给物理引擎算） | 会互相穿透 | **仿真**要用 |

注意：`<visual>` 和 `<collision>` **必须写两份几乎一样的几何**。初学者会问"为什么不能合一份"——因为它们可以故意不同（比如碰撞体简化成方盒以加快计算）。本项目为了简单，两份写成一样。

**② `<origin>` 的坑：为什么 y 和 z 都带 `/2`？**

看 `base_link`：

```xml
<origin xyz="0 0 ${base_height/2}" rpy="0 0 0"/>
<geometry><cylinder radius="${base_radius}" length="${base_height}"/></geometry>
```

`<origin>` 是**几何体的中心相对 link 原点的偏移**。而 `cylinder` 的几何原点在**圆柱正中心**。

我们希望"底座底面贴着世界原点、往上长"，所以要把中心抬高半个高度：`z = base_height/2`。

**搞混的后果**：零件位置整体偏移半个高度，越靠末端累积误差越大，最后机械臂看起来"错位"。

**一条经验法则**：写 `<origin>` 时总问自己一句——**"这个几何体的原点在哪，我想让它对齐到哪？"**

**③ 关节的位置从哪来？**

`shoulder_joint` 的 `<origin xyz="0 0 ${link1_height}">` 意思是：**link2 的原点，相对于 link1 的原点，往 z 方向移动一个 link1_height**（也就是移到 link1 的顶端）。

所以本项目是用"**上一根杆的顶端 = 下一根杆的起点**"这种首尾相接的方式建模的。你可以顺着数一遍：`base_height` → `link1_height` → `link2_length` → `link3_length`，正好把机械臂从地面串到末梢。

**④ `rpy` 一直是 `0 0 0`，那旋转靠什么？**

靠 `<axis>`！这是最容易混的一点：

- `<origin rpy="...">` 是**关节的固定安装角度**——装好了就不动；
- `<axis xyz="...">` 是**关节的运动轴**——关节绕着/沿着它转或滑。

本项目：
| 关节 | axis | 意思 |
|------|------|------|
| `base_joint` | `0 0 1` | 绕 **Z 轴**转 → 底座左右转身（偏航） |
| `shoulder_joint` | `0 1 0` | 绕 **Y 轴**转 → 大臂前后俯仰 |
| `elbow_joint` | `0 1 0` | 绕 **Y 轴**转 → 小臂前后俯仰 |

**为什么肩和肘都用 Y 轴？** 因为机械臂竖直向上伸展时，绕 Y 轴转动等于让它在 XZ 平面内前后弯——这就是最常见的"平面机械臂"运动方式。

> **想加深理解**：把 `shoulder_joint` 的 axis 临时改成 `1 0 0`，重新启动 display，你会看到大臂改成左右摇摆了。**亲手改一次比看十遍文档管用。**

**⑤ `<limit>` 三个数字**

```xml
<limit lower="-1.5708" upper="1.5708" effort="10.0" velocity="1.5"/>
```

| 参数 | 含义 | 单位 |
|------|------|------|
| `lower` / `upper` | 角度（或位移）范围 | 弧度 / 米 |
| `effort` | 最大力矩 | N·m |
| `velocity` | 最大速度 | rad/s |

**`revolute` 和 `prismatic` 必须有 `<limit>`**，`fixed` 和 `continuous` 不需要。漏了会导致 URDF 校验失败。

角度换算速记：`π ≈ 3.14159`（180°），`π/2 ≈ 1.5708`（90°），`1.0 rad ≈ 57.3°`。

### 批次 C · 夹爪（含一个真实的坑）

#### 🎯 这部分的难点

夹爪是**两片**：一片固定（上颚连在底座上）、一片活动（沿 Y 轴滑过去夹住东西）。

- 固定爪不再单独建 link，而是作为 `gripper_base` 的**第二个 `<visual>`/`<collision>`**（一个 link 可以有多个几何体！）；
- 两片指各建一个 link（`finger_right` / `finger_left`），用 **`revolute`** 关节驱动，左指用 `<mimic>` 反向跟随右指。

#### ⌨️ 完整代码（追加到 `</robot>` 之前）

```xml
  <!-- ================= 7. 夹爪（一个固定关节 + 两个旋转指） ================= -->

  <joint name="gripper_joint" type="fixed">
    <parent link="link3"/>
    <child  link="gripper_base"/>
    <origin xyz="0 0 ${link3_length}" rpy="0 0 0"/>
  </joint>

  <link name="gripper_base">
    <xacro:box_inertia m="${grip_mass}" x="${grip_x}" y="${grip_y}" z="${grip_z}"/>
    <visual>
      <origin xyz="0 0 ${grip_z/2}" rpy="0 0 0"/>
      <geometry>
        <box size="${grip_x} ${grip_y} ${grip_z}"/>
      </geometry>
      <material name="col_joint"><color rgba="${col_joint}"/></material>
    </visual>
    <collision>
      <origin xyz="0 0 ${grip_z/2}" rpy="0 0 0"/>
      <geometry>
        <box size="${grip_x} ${grip_y} ${grip_z}"/>
      </geometry>
    </collision>
  </link>

  <!-- 右指（主动）：绕 X 轴旋转，指在 YZ 平面内摆动。
       角度为负时指尖向 +Y 偏 → 向对侧靠拢 = "闭合"；0.0 即"张开到竖直"。
       关键：关节轴放在指的根部、指沿 +Z 伸出，
       所以 0 位时重力矩为 0，不会像平移关节那样被沿运动方向的重力分量顶住。 -->
  <joint name="finger_right_joint" type="revolute">
    <parent link="gripper_base"/>
    <child  link="finger_right"/>
    <origin xyz="0 ${-grip_y/2 + finger_size/2} ${grip_z}" rpy="0 0 0"/>
    <axis xyz="1 0 0"/>
    <limit lower="-0.4" upper="0.0" effort="1000.0" velocity="1.0"/>
  </joint>

  <link name="finger_right">
    <xacro:box_inertia m="${finger_mass}" x="${finger_size}" y="${finger_size}" z="${finger_len}"/>
    <visual>
      <origin xyz="0 0 ${finger_len/2}" rpy="0 0 0"/>
      <geometry>
        <box size="${finger_size} ${finger_size} ${finger_len}"/>
      </geometry>
      <material name="col_base"><color rgba="${col_base}"/></material>
    </visual>
    <collision>
      <origin xyz="0 0 ${finger_len/2}" rpy="0 0 0"/>
      <geometry>
        <box size="${finger_size} ${finger_size} ${finger_len}"/>
      </geometry>
    </collision>
  </link>

  <!-- 左指（从动）：mimic 右指、乘 -1，两指对称开合。
       它不需要控制器去驱动 —— 硬件层会自动让它跟随右指。 -->
  <joint name="finger_left_joint" type="revolute">
    <parent link="gripper_base"/>
    <child  link="finger_left"/>
    <origin xyz="0 ${grip_y/2 - finger_size/2} ${grip_z}" rpy="0 0 0"/>
    <axis xyz="1 0 0"/>
    <limit lower="0.0" upper="0.4" effort="1000.0" velocity="1.0"/>
    <mimic joint="finger_right_joint" multiplier="-1" offset="0"/>
  </joint>

  <link name="finger_left">
    <xacro:box_inertia m="${finger_mass}" x="${finger_size}" y="${finger_size}" z="${finger_len}"/>
    <visual>
      <origin xyz="0 0 ${finger_len/2}" rpy="0 0 0"/>
      <geometry>
        <box size="${finger_size} ${finger_size} ${finger_len}"/>
      </geometry>
      <material name="col_base"><color rgba="${col_base}"/></material>
    </visual>
    <collision>
      <origin xyz="0 0 ${finger_len/2}" rpy="0 0 0"/>
      <geometry>
        <box size="${finger_size} ${finger_size} ${finger_len}"/>
      </geometry>
    </collision>
  </link>
```

#### 🔍 代码怎么读

**① 为什么夹爪不用"平移"，而是"两个旋转指"**

这是**照搬原项目 akabot 的做法**，也是踩过坑之后的定型方案。

新手最直觉的写法是"一片活动爪沿 Y 轴滑过去夹住东西"（`prismatic` 关节）。本项目一开始就是那么写的，
但实测发现它在**机械臂倾斜时会完全失效**——完整排查过程写在 **05 章 5.8.1**，这里只给结论：

> 本机 Gazebo 的位置驱动增益被**硬编码为 0.1 且改不了**（写 URDF 的 `<param>` 或写 YAML 都被静默忽略），
> 所以驱动能力很弱。而平移关节的运动方向一旦和重力不平行，重力就会**沿运动方向**产生持续阻力，推不动。
> **旋转关节把重力变成"绕轴力矩"**，量级小得多，两指对称还能互相抵消。

所以夹爪定为：**两指都绕 X 轴旋转 + 一个 `mimic` 从动**。

**② 右指（主动）的几何是怎么摆的**

```xml
<joint name="finger_right_joint" type="revolute">
  <origin xyz="0 ${-grip_y/2 + finger_size/2} ${grip_z}" rpy="0 0 0"/>
  <axis xyz="1 0 0"/>
  <limit lower="-0.4" upper="0.0" effort="1000.0" velocity="1.0"/>
</joint>
```

逐项解释：

- `origin` 的 `y = -grip_y/2 + finger_size/2`：让指**贴着底板边缘内侧**。`-grip_y/2` 走到边缘，
  再退半个自身宽度、让指的**中心**落在里面——**"先到边界、再退半个自身尺寸"是 URDF 定位几何体的通用套路**；
- `origin` 的 `z = grip_z`：关节轴正好落在**底板顶面**上，指从顶面往上长；
- `<axis xyz="1 0 0"/>`：绕 **X 轴**旋转，指在 **YZ 平面**内摆动，也就是朝对侧"咬合"；
- `lower="-0.4" upper="0.0"`：指只能往**负方向**转（向对侧靠拢）。`0.0` 就是"竖直张开"的初始状态。

关键点：指沿 **+Z 伸出、关节轴在指的根部**，所以张开状态（角度 0）时重力矩为 0，
转动过程中重力矩也很小——**这是它比平移关节可靠的根本原因**。

**③ 左指靠 `mimic` 自动跟随**

```xml
<joint name="finger_left_joint" type="revolute">
  <origin xyz="0 ${grip_y/2 - finger_size/2} ${grip_z}" rpy="0 0 0"/>
  <axis xyz="1 0 0"/>
  <limit lower="0.0" upper="0.4" effort="1000.0" velocity="1.0"/>
  <mimic joint="finger_right_joint" multiplier="-1" offset="0"/>
</joint>
```

`<mimic>` 的意思是：**"我的值 = 目标关节的值 × multiplier + offset"**。
这里 multiplier = `-1`，所以左指 = 右指的反向 → **两指对称开合**，像剪刀一样。

它有两个好处：

| 好处 | 说明 |
|------|------|
| **省一个控制器** | 只控右指，左指自动跟着走 |
| **天然对称** | 不用担心两指角度的同步误差 |

注意 `limit` 与右指是**镜像**的（右指 `-0.4~0.0`，左指 `0.0~0.4`），因为两者旋转方向相反。
**写错这一处，闭合时会看到两片指往同一边转。**

**④ 三处名字必须完全一致（本书最容易错的地方）**

```
ros2_arm_core.xacro            <joint name="finger_right_joint">
ros2_arm.ros2_control.xacro    <joint name="finger_right_joint">
ros2_arm_controllers.yaml      joint: finger_right_joint
```

差一个字母 → 步骤 13 会报 `controller failed to load`。改完记得 `grep` 对一遍。

> 💡 **如果你还是想试试"平移夹爪"**：可以写，但请记住它在机械臂倾斜时会失效，
> 而且被 `ABORTED` 时**关节是纹丝不动的**（不是"差一点没到位"）。
> 想亲手复现这个现象 → 见 05 章 5.8.1 的实测表格。

- `ros2_arm_gz.urdf.xacro` —— 带控制带仿真（步骤 12 写）。

```xml
</robot>
```

**只有 5 行。**

### 🔍 代码怎么读

**`$(find ros2_arm_description)` 是什么？**

它是"**运行时**查找包路径"的占位符。xacro 执行时会把它替换成这个包在 `install/` 里的实际路径。

**为什么不用相对路径或绝对路径？**
- 绝对路径 `~/ros2_arm/src/...` —— 换台机器就废了；
- 相对路径 `../urdf/...` —— xacro 的 include 是相对于**执行时的工作目录**，你在哪个目录下敲命令结果都不一样，极不稳定；
- `$(find 包名)` —— 由 ament 索引统一解析，**无论从哪个目录执行都正确**。这是 ROS 2 的标准写法。

**代价**：它要求这个包**已经被编译并 source 过**。所以你能看到一条隐藏依赖链：

```
写 core.xacro → colcon build（把 urdf/ 装进 install）→ source → $(find) 才能解析成功
```

## 步骤 7 · 写 `display.launch.py` ✅ 里程碑 ②

### 🎯 这一步做什么

一条命令启动 4 个节点，在 RViz 里看到机械臂，并能用滑块手动摆姿势。

**launch 文件是"总指挥"**：把原本要开 4 个终端分别敲的命令，写进一个 Python 文件里一次启动。

### 📄 要写的文件

```
src/ros2_arm_description/launch/display.launch.py
```

### ⌨️ 完整代码

```python
"""在 RViz 里显示 ros2_arm 模型，并可用滑块手动摆关节。"""
import os

from ament_index_python.packages import get_package_share_directory
from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch.conditions import IfCondition, UnlessCondition
from launch.substitutions import Command, LaunchConfiguration
from launch_ros.actions import Node
from launch_ros.parameter_descriptions import ParameterValue


def generate_launch_description():
    pkg_share = get_package_share_directory('ros2_arm_description')
    xacro_file = os.path.join(pkg_share, 'urdf', 'ros2_arm.urdf.xacro')
    rviz_config = os.path.join(pkg_share, 'rviz', 'display.rviz')

    use_gui = LaunchConfiguration('use_gui')

    # Command 会执行 "xacro <文件>" 并把输出（纯 URDF 文本）作为参数传给节点
    robot_description = {
        'robot_description': ParameterValue(Command(['xacro ', xacro_file]), value_type=str)
    }

    # RViz 配置文件还不存在时，就让 rviz2 用默认配置启动（避免报错吓人）
    rviz_args = ['-d', rviz_config] if os.path.exists(rviz_config) else []

    return LaunchDescription([
        DeclareLaunchArgument('use_gui', default_value='true',
                              description='true=用滑块手动摆关节，false=用默认值'),

        # 把 URDF 转成 TF 树（RViz 靠它知道零件之间的位置关系）
        Node(package='robot_state_publisher', executable='robot_state_publisher',
             output='screen', parameters=[robot_description]),

        # 滑块窗口：手动给每个关节设角度
        Node(package='joint_state_publisher_gui', executable='joint_state_publisher_gui',
             condition=IfCondition(use_gui)),

        # 无滑块时的替代：给关节发默认值
        Node(package='joint_state_publisher', executable='joint_state_publisher',
             condition=UnlessCondition(use_gui)),

        Node(package='rviz2', executable='rviz2', output='screen', arguments=rviz_args),
    ])
```

### 🔍 代码怎么读

**① launch 文件的固定骨架**

```python
def generate_launch_description():        # ← 函数名必须是这个
    ...
    return LaunchDescription([ ... ])      # ← 必须返回一个 LaunchDescription，里面是动作列表
```

launch 系统会去找这个函数名。**名字写错就等于文件不存在**，而且报错很含糊。

**② 最核心的一行**

```python
robot_description = {
    'robot_description': ParameterValue(Command(['xacro ', xacro_file]), value_type=str)
}
```

拆开看：

| 部分 | 作用 |
|------|------|
| `Command(['xacro ', xacro_file])` | 启动时执行 `xacro /path/to/xx.xacro`，把**标准输出**当作值 |
| `ParameterValue(..., value_type=str)` | **强制声明这是字符串** |
| `{'robot_description': ...}` | 要传给节点的参数字典 |

**`value_type=str` 非常重要**：`robot_description` 是一大段 XML 文本，launch 默认会尝试把它当 YAML 解析，遇到 XML 的特殊字符就崩，报一堆很难懂的 YAML 解析错误。**显式声明 `str` 就不会。**

**③ 为什么 `robot_state_publisher` 是必需节点？**

它做一件事：**把 URDF 里的"零件相对位置" + 关节当前角度，算成 TF 坐标变换树**。

RViz 靠 TF 树才知道"大臂应该画在小臂前面的什么位置"。**没有它，RViz 里什么都看不见**（或者所有零件叠在原点）。

**④ 为什么有两个 joint_state_publisher？**

| 节点 | 什么时候跑 | 作用 |
|------|-----------|------|
| `joint_state_publisher_gui` | `use_gui:=true`（默认） | 弹滑块窗口，你拖动它就发关节角度 |
| `joint_state_publisher` | `use_gui:=false` | 不发滑块，只发全 0 默认值 |

**为什么必须二选一？** 因为**两个节点都发布 `/joint_states` 话题**，同时跑会打架（消息交替覆盖，模型在两种姿态间抖动）。用 `IfCondition` / `UnlessCondition` 保证**永远只有一个在跑**。

**这是"话题独占"的典型场景**，以后你写自己的节点也要注意这个问题。

**⑤ `rviz_args` 那一行的技巧**

```python
rviz_args = ['-d', rviz_config] if os.path.exists(rviz_config) else []
```

`os.path.exists` 判断 RViz 配置文件在不在——不在就用空参数启动（RViz 打开默认界面）。

**为什么这么写？** 因为你现在还没做 RViz 配置（`rviz/` 是空的）。如果不判断，`rviz2 -d 不存在的文件` 会报错，新手会以为整个启动失败了。**这种"优雅降级"的写法在实际项目里很常见。**

### ⚠️ 坑（真实踩过，编号 C-1）

**`pkill` 会杀掉自己。** 如果你直接敲：

```bash
pkill -f 'ros2 launch'      # ← 危险！你的这条命令自身也含 "ros2 launch" 字符串
```

`pkill -f` 匹配的是**完整命令行**。而你这条 `bash -c "pkill -f 'ros2 launch'"` 的命令行里正好包含这个字符串，**它把自己也匹配上了，于是先把自己杀了**，后面的清理自然没执行。

**正确写法**：在匹配串里加方括号打断字面匹配：

```bash
pkill -f 'ros2 launc[h]'
```

`ros2 launc[h]` 这个正则能匹配 `ros2 launch`（因为 `[h]` 就是 `h`），但**它自身的字符串是 `ros2 launc[h]`，不含 "ros2 launch"**，所以不会自杀。

**这条技巧在清理任何进程时都通用**，值得记住。

# 阶段三 · 让关节能被控制

> 目标：声明"哪些关节可以被命令控制"。**这一步不启动任何东西**，只是把"控制接口"写进模型。
> 对应第 06 章的核心内容。

## 步骤 8 · 写 `ros2_arm.ros2_control.xacro`

### 🎯 这一步做什么

给每个受控关节声明**命令接口**和**状态接口**，并指定底层硬件插件。

### 🔍 先搞懂：什么是"接口"

`ros2_control` 的核心思想是**把"上层控制逻辑"和"底层硬件驱动"解耦**。中间的桥梁就是**接口（interface）**。

| 接口类型 | 方向 | 谁写谁读 | 例子 |
|---------|------|---------|------|
| `command_interface` | 上层 → 硬件 | 控制器**写**，硬件**读** | "把肩关节转到 0.5 弧度" |
| `state_interface` | 硬件 → 上层 | 硬件**写**，控制器**读** | "肩关节当前是 0.48 弧度" |

**一个必记的规则**：**没声明的接口，控制器就动不了那个关节。** 这是新手最常见的"控制器 active 但关节不动"的原因之一。

### 📄 要写的文件

```
src/ros2_arm_description/urdf/ros2_arm.ros2_control.xacro   ← 当前是空文件
```

### ⌨️ 完整代码

```xml
<?xml version="1.0"?>
<!-- ============================================================
     ros2_arm.ros2_control.xacro
     作用：声明每个关节的 command / state 接口，以及底层硬件插件
     关键：插件名由调用方传入（仿真 / 真机不同），上层代码不变
     ============================================================ -->
<robot xmlns:xacro="http://www.ros.org/wiki/xacro">

  <xacro:macro name="ros2_arm_ros2_control" params="name plugin_name">

    <ros2_control name="${name}" type="system">
      <!-- 底层硬件插件：仿真时是 ign_ros2_control；真机时是你自己写的组件 -->
      <hardware>
        <plugin>${plugin_name}</plugin>
      </hardware>

      <!-- 关节 1：底座旋转 -->
      <joint name="base_joint">
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
      </joint>

      <!-- 关节 2：肩 -->
      <joint name="shoulder_joint">
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
      </joint>

      <!-- 关节 3：肘 -->
      <joint name="elbow_joint">
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
      </joint>

      <!-- 关节 4/5：夹爪两指（旋转关节，一个主动 + 一个 mimic 联动） -->
      <joint name="finger_right_joint">
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
      </joint>

      <joint name="finger_left_joint">
        <!-- 从动关节：声明跟随 finger_right_joint，倍数 -1（反向对称） -->
        <param name="mimic">finger_right_joint</param>
        <param name="multiplier">-1</param>
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
      </joint>

    </ros2_control>
  </xacro:macro>

</robot>
```

### 🔍 代码怎么读

**① 为什么整份文件都是一个 `<xacro:macro>`？**

因为它**不是一个可以直接用的模型**，而是一个"可插拔的零件"。谁调用它，就传进自己的 `name` 和 `plugin_name`：

```xml
<xacro:ros2_arm_ros2_control name="Ros2ArmSystem" plugin_name="ign_ros2_control/IgnitionSystem"/>
```

**这就是"仿真 / 真机共用同一套上层代码"的关键设计**：

| 场景 | plugin_name | 效果 |
|------|------------|------|
| 仿真 | `ign_ros2_control/IgnitionSystem` | 指令发给 Gazebo 里的虚拟电机 |
| 真机 | 你自己写的硬件组件 | 指令发给真实舵机（可能是 I2C / 串口） |

**上层控制器、yaml 配置、launch 文件全都不用改。** 这是本项目最重要的架构决策之一。

**② 为什么是 5 个关节？**

```xml
<joint name="base_joint">         ✅ 有
<joint name="shoulder_joint">     ✅ 有
<joint name="elbow_joint">        ✅ 有
<joint name="finger_right_joint"> ✅ 有（主动）
<joint name="finger_left_joint">  ✅ 有（从动，mimic）
<joint name="world_base_joint"> ❌ 没有（fixed，焊死的，不需要控制）
<joint name="gripper_joint">    ❌ 没有（fixed，同上）
```

**规则：只有"会动的关节"才需要接口。** `fixed` 关节是焊死的，没有可控制的量。

**③ 为什么每个关节都声明 `<state_interface name="velocity"/>`？**

- `position` 是必需的（要知道转到哪了）；
- `velocity` 是**推荐**加的：很多控制器（尤其是轨迹控制器）在计算时要用到速度，缺了会警告或不准。

**注意 `command_interface` 只声明了 `position`，没有 `velocity`。**

**为什么？** 因为本例用的是**位置控制**模式——上层只说"到哪去"，速度由控制器内部算。这既简单又稳定。

**如果你想改成速度控制**，就加 `<command_interface name="velocity"/>` 并改 yaml 里的 `command_interfaces`。**不写对应的接口却去配对应的控制器，是"控制器加载失败"的常见原因。**

**④ 数一下接口总数（后面要拿来验收）**

```
command_interface : 4 个关节 × 1 = 4
state_interface   : 4 个关节 × 2 = 8
```

## 步骤 9 · 写 `ros2_arm_controllers.yaml` ✅ 里程碑 ③

### 🎯 这一步做什么

告诉 `controller_manager`：**加载哪几个控制器、每个控制器管哪些关节。**

### 📄 要写的文件

```
src/ros2_arm_bringup/config/ros2_arm_controllers.yaml   ← 当前是空文件
```

### ⌨️ 完整代码

```yaml
# ============================================================
# ros2_arm_controllers.yaml
# 由 controller_manager 读取（路径写在 ros2_arm_gz.urdf.xacro 里）
# ============================================================
controller_manager:
  ros__parameters:
    update_rate: 100          # 控制频率 100 Hz（每 10 ms 下发一次指令）

    # ---- 声明三个控制器（这里只声明"有哪些"，参数在下面分开写） ----
    joint_state_broadcaster:
      type: joint_state_broadcaster/JointStateBroadcaster

    ros2_arm_controller:
      type: joint_trajectory_controller/JointTrajectoryController

    finger_controller:
      type: position_controllers/GripperActionController

# ---- 控制器 1：机械臂轨迹控制器 ----
ros2_arm_controller:
  ros__parameters:
    joints:                   # 顺序可以任意，但名字必须与 URDF 完全一致
      - base_joint
      - shoulder_joint
      - elbow_joint
    command_interfaces:
      - position
    state_interfaces:
      - position
      - velocity
    allow_nonzero_velocity_at_trajectory_end: false   # 轨迹终点速度归零，避免抖动

# ---- 控制器 2：夹爪（只控主动指，从动指由 mimic 自动跟随）----
finger_controller:
  ros__parameters:
    joint: finger_right_joint
```

### 🔍 代码怎么读

**① YAML 的结构：三段，各管一件事**

| 段 | 作用 |
|----|------|
| `controller_manager` | 只声明"有哪三个控制器"，以及全局控制频率 |
| `ros2_arm_controller` | 逐个配参数：管哪些关节、用哪些接口 |
| `finger_controller` | 同上 |

**为什么不把所有东西写在一段里？** 因为 ROS 2 的参数机制是**按节点命名的**：`controller_manager` 是个节点，每个控制器加载后也**各自成为一个节点**。所以参数必须分别挂在对应的节点名下。

**这是 ROS 2 参数系统最容易绕晕的地方，记住这个对应关系：**

```
controller_manager/ros__parameters/          ← 参数给 controller_manager 这个节点
      └── <控制器名>:
            type: ...                        ← 只声明类型

<控制器名>/ros__parameters/                   ← 参数给"控制器名"这个节点
      └── joints: [...]                      ← 具体的关节列表
```

**② 三个控制器分别是什么**

| 控制器 | 类型 | 干什么 | 为什么必须有 |
|--------|------|--------|-------------|
| `joint_state_broadcaster` | `JointStateBroadcaster` | 把关节状态**广播**成 `/joint_states` 话题 | **没有它，RViz 和 MoveIt 都不知道机械臂在哪** |
| `ros2_arm_controller` | `JointTrajectoryController` | 接收**轨迹**（带时间戳的路径点序列）并执行 | 机械臂运动的主通道 |
| `finger_controller` | `GripperActionController` | 夹爪专用，接收"开/合"指令 | 夹爪用 action 接口更自然 |

**注意 `joint_state_broadcaster` 是"广播器"不是"控制器"**——它不下发指令，只上报状态。很多人第一次会以为它可有可无，**实际上没有它整个可视化和规划全部瘫痪。**

**③ `joints` 列表的顺序重要吗？**

```yaml
joints:
  - base_joint
  - shoulder_joint
  - elbow_joint
```

**顺序不重要，但名字必须和 URDF 里一模一样。** 控制器内部会按名字去匹配，顺序只决定它内部数组的排列（发轨迹时你可以按自己的顺序给 `joint_names`）。

**⚠️ 但顺序在另一个地方很重要**：你发轨迹时给的 `positions` 数组，**必须和你在消息里写的 `joint_names` 顺序对应**，而不是和 yaml 里的顺序对应。这个坑见步骤 14。

**④ `update_rate: 100` 是什么意思**

控制器的**运算频率**：每秒算 100 次，也就是每 10 ms 下发一次指令。

| 值 | 效果 |
|----|------|
| 100 | 平滑，CPU 占用适中（推荐） |
| 1000 | 更平滑，CPU 明显上升 |
| 10 | 卡顿、抖动 |

**注意它必须 ≤ 仿真步长的倒数。** 本项目 world 里 `max_step_size = 0.001`（1 ms），所以理论上限是 1000 Hz，取 100 很安全。

**⑤ `allow_nonzero_velocity_at_trajectory_end: false`**

轨迹执行到终点时，允许不允许还有残余速度。

- `false` —— 强制终点速度归零，**结束时不会突然"甩"一下**；
- `true` —— 允许带速度通过终点，适合"连续多段轨迹"的场景。

本项目取 `false`：更稳定，更适合练习。

## 步骤 10 · 写 `arm_world.sdf`

### 🎯 这一步做什么

建一个"虚拟世界"：物理引擎参数 + 光照 + 地面 + 一个练习用的方块。

**为什么必须自己写 world？** Gazebo 可以不带 world 启动（会加载一个空世界），但那样没有地面、光照参数也不受控。**一个项目的 world 文件应该被纳入版本管理**，保证所有人的仿真环境完全一致。

### 📄 要写的文件

```
src/ros2_arm_gazebo/worlds/arm_world.sdf
```

### ⌨️ 完整代码

```xml
<?xml version="1.0" ?>
<!-- ============================================================
     arm_world.sdf
     作用：为 ros2_arm 提供一个带地面、光照、物理参数的虚拟世界
     ============================================================ -->
<sdf version="1.8">
  <world name="arm_world">

    <!-- ---------- 1. 物理引擎参数 ---------- -->
    <physics name="1ms" type="ignored">
      <max_step_size>0.001</max_step_size>   <!-- 每步 1 ms -->
      <real_time_factor>1.0</real_time_factor><!-- 尽量与真实时间同速 -->
    </physics>

    <!-- ---------- 2. 必备的系统插件（少了仿真就不工作） ---------- -->
    <plugin filename="ignition-gazebo-physics-system"
            name="ignition::gazebo::systems::Physics"/>
    <plugin filename="ignition-gazebo-user-commands-system"
            name="ignition::gazebo::systems::UserCommands"/>
    <plugin filename="ignition-gazebo-scene-broadcaster-system"
            name="ignition::gazebo::systems::SceneBroadcaster"/>

    <!-- ---------- 3. 光照 ---------- -->
    <light type="directional" name="sun">
      <cast_shadows>true</cast_shadows>
      <pose>0 0 10 0 0 0</pose>
      <diffuse>0.8 0.8 0.8 1</diffuse>
      <specular>0.2 0.2 0.2 1</specular>
      <direction>-0.5 0.1 -0.9</direction>
    </light>

    <!-- ---------- 4. 地面 ---------- -->
    <model name="ground_plane">
      <static>true</static>
      <link name="link">
        <collision name="collision">
          <geometry>
            <plane><normal>0 0 1</normal><size>20 20</size></plane>
          </geometry>
        </collision>
        <visual name="visual">
          <geometry>
            <plane><normal>0 0 1</normal><size>20 20</size></plane>
          </geometry>
          <material>
            <ambient>0.75 0.75 0.75 1</ambient>
            <diffuse>0.75 0.75 0.75 1</diffuse>
          </material>
        </visual>
      </link>
    </model>

    <!-- ---------- 5. 一个练习用的方块（第 08 章可以试着去"够"它） ---------- -->
    <model name="target_cube">
      <static>true</static>
      <pose>0.32 0 0.03 0 0 0</pose>
      <link name="link">
        <collision name="collision">
          <geometry><box><size>0.06 0.06 0.06</size></box></geometry>
        </collision>
        <visual name="visual">
          <geometry><box><size>0.06 0.06 0.06</size></box></geometry>
          <material>
            <ambient>0.2 0.6 0.9 1</ambient>
            <diffuse>0.2 0.6 0.9 1</diffuse>
          </material>
        </visual>
      </link>
    </model>

  </world>
</sdf>
```

### 🔍 代码怎么读

**① SDF 和 URDF 是两种不同格式**

| 文件 | 描述什么 | 谁读它 |
|------|---------|--------|
| URDF / xacro | **机器人**（link + joint） | robot_state_publisher、MoveIt |
| SDF | **世界**（地面、光照、物理、障碍物） | Gazebo 本身 |

**Gazebo Fortress 用的是 SDF 1.8。** 语法上和 URDF 有点像（都是 XML），但概念不同——SDF 的 `<model>` 里也可以有 `<link>`，但那是"世界里的物体"，不是机器人。

**② `<physics>` —— 决定仿真的"真实感"**

```xml
<max_step_size>0.001</max_step_size>
```

仿真器是**离散**推进的：每算一步就前进 1 ms。这个值越小越精确，但计算量越大。

| 值 | 效果 |
|----|------|
| 0.001（1 ms） | 精确，**推荐**。机械臂不会莫名抖动 |
| 0.01（10 ms） | 快，但快速运动时可能穿透、抖动 |

`real_time_factor = 1.0` 的意思是"跑得和真实时间一样快"。设成 `0` 表示"不限速，全力跑"（适合跑批处理测试）。

**⚠️ 注意别写成 `<max_step_size>0.1</max_step_size>`** —— 那会让仿真每步前进 0.1 秒，机械臂会剧烈抖动甚至飞出去。

**③ 三个系统插件——**少一个世界就跑不起来**

| 插件 | 作用 | 缺了会怎样 |
|------|------|-----------|
| `Physics` | 物理引擎（重力、碰撞） | 什么都不动 |
| `UserCommands` | 允许外部命令（比如"生成机器人"） | **`ros_gz_sim create` 失败，机器人放不进去** |
| `SceneBroadcaster` | 向外发布场景信息 | **Gazebo 界面一片空白** |

**这三个是 Gazebo Fortress 的最小必需集**，写 world 就照抄这三行。

**④ `<static>true</static>` 是什么**

表示"这个物体是固定的，物理引擎不用算它"。地面和练习方块都设了 `true`——**地面当然不动，方块我们也希望它乖乖待着当靶子**（而不是被机械臂一碰就滚走）。

**想练抓取的话**，把 `target_cube` 的 `<static>true</static>` 去掉，它就会变成一个可以被推、被抓起的动态物体。

**⑤ `target_cube` 的位置是算过的**

```xml
<pose>0.32 0 0.03 0 0 0</pose>
```

`z = 0.03` 是方块边长的一半（0.06/2）——**让方块底面正好贴地**。这是"让物体贴着地面"的通用算法。

`x = 0.32` 大致等于机械臂水平伸展时的可达距离（大臂 0.25 + 小臂 0.22 ≈ 0.47 的最大值，0.32 是比较舒服的中间位置）。

**`<pose>` 是 6 个数字：`x y z roll pitch yaw`。** 这里只用了前三个（位置），后三个（姿态）全 0 表示"不旋转"。

## 步骤 11 · 写 `ros2_arm_bridge.yaml`

### 🎯 这一步做什么

定义"**哪些 Gazebo 话题**"要桥接到"**哪些 ROS 2 话题**"。

### 🔍 先搞懂：为什么需要"桥"

**Gazebo 和 ROS 2 是两套独立的通信系统**，各说各的语言：

| | ROS 2 | Gazebo |
|--|-------|--------|
| 消息类型 | `rosgraph_msgs/msg/Clock` | `gz.msgs.Clock` |
| 中间件 | DDS | gz-transport |
| 话题名 | `/clock` | `/clock` |

`parameter_bridge` 这个节点就是**翻译官**：把一边的消息类型翻译成另一边。

### 📄 要写的文件

```
src/ros2_arm_gazebo/config/ros2_arm_bridge.yaml
```

### ⌨️ 完整代码

```yaml
# ============================================================
# ros2_arm_bridge.yaml
# 由 parameter_bridge 读取：定义"哪些 gz 话题 ↔ 哪些 ROS 话题"
# ============================================================

# 仿真时钟：Gazebo 的时间基准，所有开了 use_sim_time 的节点都要它
- ros_topic_name: "clock"
  gz_topic_name: "clock"
  ros_type_name: "rosgraph_msgs/msg/Clock"
  gz_type_name: "gz.msgs.Clock"
  direction: GZ_TO_ROS
```

**注意这是个 YAML 列表**（顶层是 `-` 开头的条目），不是字典。这和步骤 9 的格式不一样。

### 🔍 代码怎么读

**① 只桥一个 `clock` 就够了吗？**

**对本项目来说够，但这是个容易误解的点，必须讲清楚。**

正常情况下，`/joint_states`（关节状态）和轨迹指令**都要桥接**。但本项目用的是 `ros2_control` 方案，情况特殊：

```
Gazebo 里的 ign_ros2_control 插件 ──(直接发布 ROS 话题)──> /joint_states
                                    ↑
                          它本身就在 ROS 2 侧，不需要桥！
```

**关键理解**：`ign_ros2_control` 插件**运行在 Gazebo 进程内**，但它**直接使用 ROS 2 中间件**发布 `/joint_states`。所以这些话题**不需要经过 bridge**。

**那还剩什么需要桥？** 只有 `clock`——因为仿真时间只有 Gazebo 知道，必须翻译给 ROS 2 侧（否则 `use_sim_time:=true` 的节点会一直等时间，什么都不干）。

**什么时候需要桥更多东西？** 当你要用 Gazebo 原生的传感器时（相机、激光雷达、IMU）——那些是纯 gz 消息，必须桥。本项目没用到。

**② 五个字段的含义**

| 字段 | 含义 |
|------|------|
| `ros_topic_name` | ROS 2 侧的话题名（不带 `/` 也会被当成绝对名） |
| `gz_topic_name` | Gazebo 侧的话题名 |
| `ros_type_name` | ROS 2 的类型，格式是 `包名/msg/消息名` |
| `gz_type_name` | Gazebo 的类型，格式是 `gz.msgs.消息名` |
| `direction` | 方向：`GZ_TO_ROS` / `ROS_TO_GZ` / `BIDIRECTIONAL` |

**方向的记忆法**：`clock` 是 Gazebo **产生**时间、ROS 2 **消费**，所以是 `GZ_TO_ROS`。

**③ 类型名写错了会怎样**

如果 `ros_type_name` 写成一个不存在的类型，`parameter_bridge` 会报 `Unable to load type [...]` 然后那条桥接被跳过（其余正常）。**所以 bridge 的问题往往表现为"某个话题就是没有"，而不是进程崩溃。**


**必须是全小写 `clock`。** 写成 `Clock` 会在运行时静默失败——话题没出现，但没有任何报错。**这类"静默失败"是最难查的**，所以名字一定要两边核对。

## 步骤 12 · 写仿真用总装 `ros2_arm_gz.urdf.xacro`

### 🎯 这一步做什么

把 `core.xacro`（零件）+ `ros2_control.xacro`（接口）+ Gazebo 插件**拼成仿真用的机器人**。

**这是整个项目"零件组装"最关键的一个文件**——只有 20 行，但每一行都有含义。

### 📄 要写的文件

```
src/ros2_arm_description/urdf/ros2_arm_gz.urdf.xacro
```

### ⌨️ 完整代码

```xml
<?xml version="1.0"?>
<!-- 用途：Gazebo 仿真（含 ros2_control 硬件接口与插件） -->
<robot xmlns:xacro="http://www.ros.org/wiki/xacro" name="ros2_arm">

  <!-- 1. 引入零件库 -->
  <xacro:include filename="$(find ros2_arm_description)/urdf/ros2_arm_core.xacro"/>
  <!-- 2. 引入 ros2_control 接口声明（第 06 章写的文件） -->
  <xacro:include filename="$(find ros2_arm_description)/urdf/ros2_arm.ros2_control.xacro"/>

  <!-- 3. 声明硬件接口：仿真时插 ign_ros2_control 插件 -->
  <xacro:ros2_arm_ros2_control name="Ros2ArmSystem" plugin_name="ign_ros2_control/IgnitionSystem"/>

  <!-- 4. 让 Gazebo 加载 ros2_control 插件（controller_manager 由此诞生） -->
  <gazebo>
    <plugin filename="ign_ros2_control-system" name="ign_ros2_control::IgnitionROS2ControlPlugin">
      <parameters>$(find ros2_arm_bringup)/config/ros2_arm_controllers.yaml</parameters>
    </plugin>
  </gazebo>

</robot>
```

### 🔍 代码怎么读

**这是全项目最值得逐行读的文件，四段各有玄机。**

**① 第 1、2 段：include 零件和接口**

```xml
<xacro:include filename="$(find ros2_arm_description)/urdf/ros2_arm_core.xacro"/>
<xacro:include filename="$(find ros2_arm_description)/urdf/ros2_arm.ros2_control.xacro"/>
```

注意：**`include` 只是"把文件内容搬进来"，并不会自动生成任何东西。** 特别是第二个文件——它是**宏定义**，include 进来只是"让宏可以用"，还得**手动调用**（就是第 3 段）。

**这是新手最常困惑的地方**："我不是 include 了 ros2_control.xacro 吗，怎么没生效？"——因为**光 include 不够，还要调用宏。**

**② 第 3 段：调用宏，声明接口**

```xml
<xacro:ros2_arm_ros2_control name="Ros2ArmSystem" plugin_name="ign_ros2_control/IgnitionSystem"/>
```

这行把步骤 8 定义的宏**展开成实际的 `<ros2_control>` 标签**，并传入两个参数：

| 参数 | 值 | 含义 |
|------|-----|------|
| `name` | `Ros2ArmSystem` | 这套控制系统的名字（自定义） |
| `plugin_name` | `ign_ros2_control/IgnitionSystem` | **底层硬件插件**——这里指向 Gazebo 仿真 |

**换成真机时，只改这一行的 `plugin_name` 就够了。** 这就是它在宏里做参数的意义。

**③ 第 4 段：让 Gazebo 真正加载插件**

```xml
<gazebo>
  <plugin filename="ign_ros2_control-system" name="ign_ros2_control::IgnitionROS2ControlPlugin">
    <parameters>$(find ros2_arm_bringup)/config/ros2_arm_controllers.yaml</parameters>
  </plugin>
</gazebo>
```

**这一段是全项目"最反直觉"的设计，必须讲透：**

**`controller_manager` 藏在 Gazebo 里。**

新手通常以为 `controller_manager` 是某个独立进程，要自己启动。**不是的。** 流程是这样的：

```
启动 Gazebo
   ↓（Gazebo 解析 URDF，发现 <gazebo><plugin> 标签）
加载 ign_ros2_control-system 插件
   ↓（插件的名字叫 IgnitionROS2ControlPlugin）
Gazebo 进程内部启动了 controller_manager
   ↓（读 <parameters> 指向的 yaml）
知道了要加载哪三个控制器
```

**所以你在 `ros2 control list_controllers` 里看到的 `controller_manager`，其实是 Gazebo 进程里的一部分。**

**这解释了好几个新手困惑：**
- 为什么不用单独启动 `controller_manager`？→ 因为插件已经启动了；
- 为什么 Gazebo 关掉控制器就全没了？→ 因为它们在同一个进程里；
- 为什么两个仿真同时跑会出问题？→ 因为**两个 `controller_manager` 会争抢同一个 `/controller_manager` 节点名**（这个坑见步骤 13）。

**`filename` 和 `name` 的区别（这是 Gazebo 插件的固定写法）：**

| 属性 | 值 | 含义 |
|------|-----|------|
| `filename` | `ign_ros2_control-system` | **动态库名**。Gazebo 会去找 `libign_ros2_control-system.so` |
| `name` | `ign_ros2_control::IgnitionROS2ControlPlugin` | **C++ 类名**。库里的哪个类 |

**两个写错的后果不同**：`filename` 错 → 找不到库，有明确报错；`name` 错 → **能找到库但找不到类，同样有报错**。两个都不能错。

**④ 跨包引用：`$(find ros2_arm_bringup)`**

yaml 在 `bringup` 包里，但这个文件属于 `description` 包——**跨包引用**，用 `$(find)` 完全没问题。

**代价**：`ros2_arm_description` 在运行时就**依赖 `ros2_arm_bringup` 被安装**。这是有意的设计：模型（description）不该关心控制器参数（bringup 的职责），两边通过 `$(find)` 松耦合。

### ✅ 立刻验证

如果第 4 步的 `ros2_arm_controllers.yaml` **没打印出来**，说明 `$(find ros2_arm_bringup)` 解析失败了。**但注意——xacro 这时可能并不报错**，它会把 `$(find ...)` 原样留在输出里，导致仿真启动后**控制器一个都加载不出来**（因为 yaml 路径是无效的）。

**所以第 4 步的检查非常重要，不要跳。**

排查：`ros2 pkg prefix ros2_arm_bringup` 有没有输出？没有就是没 source 或没编译。

## 步骤 13 · 写 `gz_launch.py` ✅ 里程碑 ④

### 🎯 这一步做什么

写整个项目**最核心的一个 launch 文件**：一条命令拉起仿真全链路。

### 📄 要写的文件

```
src/ros2_arm_gazebo/launch/gz_launch.py
```

### ⌨️ 完整代码

```python
"""启动 ros2_arm 的完整仿真环境：Gazebo + 模型 + 桥 + 三个控制器。"""
import os

from ament_index_python.packages import get_package_share_directory
from launch import LaunchDescription
from launch.actions import (DeclareLaunchArgument, IncludeLaunchDescription,
                            TimerAction)
from launch.launch_description_sources import PythonLaunchDescriptionSource
from launch.substitutions import Command, LaunchConfiguration
from launch_ros.actions import Node
from launch_ros.parameter_descriptions import ParameterValue


def generate_launch_description():
    pkg_desc = get_package_share_directory('ros2_arm_description')
    pkg_gz = get_package_share_directory('ros2_arm_gazebo')

    xacro_file = os.path.join(pkg_desc, 'urdf', 'ros2_arm_gz.urdf.xacro')
    world_file = os.path.join(pkg_gz, 'worlds', 'arm_world.sdf')
    bridge_config = os.path.join(pkg_gz, 'config', 'ros2_arm_bridge.yaml')
    gz_sim_launch = os.path.join(
        get_package_share_directory('ros_gz_sim'), 'launch', 'gz_sim.launch.py')

    # 把 xacro 展开成 URDF，作为参数传给相关节点
    robot_description = {
        'robot_description': ParameterValue(Command(['xacro ', xacro_file]), value_type=str)
    }

    # ① 模型 → TF 树 + /robot_description 话题
    rsp = Node(package='robot_state_publisher', executable='robot_state_publisher',
               parameters=[robot_description, {'use_sim_time': True}], output='screen')

    # ② 启动 Gazebo 仿真器（-r = 立即开始运行，不要停在暂停状态）
    gazebo = IncludeLaunchDescription(
        PythonLaunchDescriptionSource(gz_sim_launch),
        launch_arguments={
            'gz_args': ['-r -v4 ', LaunchConfiguration('world')],
            'on_exit_shutdown': 'true',
        }.items(),
    )

    # ③ ROS ↔ Gazebo 话题桥（本项目桥接 clock）
    bridge = Node(package='ros_gz_bridge', executable='parameter_bridge',
                  arguments=['--ros-args', '-p', f'config_file:={bridge_config}'],
                  output='screen')

    # ④ 把机器人"生成"到世界里（从 /robot_description 话题读取模型）
    spawn = Node(package='ros_gz_sim', executable='create',
                 arguments=['-topic', 'robot_description',
                            '-name', 'ros2_arm',
                            '-x', '0.0', '-y', '0.0', '-z', '0.0'],
                 output='screen')

    # ⑤⑥⑦ 依次激活三个控制器（延迟 5 秒，等 Gazebo 把 ros2_control 插件加载完）
    def spawner(name):
        return Node(package='controller_manager', executable='spawner',
                    arguments=[name, '--controller-manager', '/controller_manager'],
                    output='screen')

    load_controllers = TimerAction(period=5.0, actions=[
        spawner('joint_state_broadcaster'),
        spawner('ros2_arm_controller'),
        spawner('finger_controller'),
    ])

    return LaunchDescription([
        DeclareLaunchArgument('world', default_value=world_file,
                              description='世界文件路径'),
        rsp,
        gazebo,
        bridge,
        spawn,
        load_controllers,
    ])
```

### 🔍 代码怎么读

**① 一条命令启动 7 个东西**

| # | 动作 | 干什么 |
|---|------|--------|
| ① | `robot_state_publisher` | 把模型变成 TF 树，并发布 `/robot_description` 话题 |
| ② | Gazebo 仿真器 | 加载世界，**并在进程内启动 controller_manager** |
| ③ | `parameter_bridge` | 桥接 `clock` |
| ④ | `create` | 从 `/robot_description` 话题读模型，**生成**到世界里 |
| ⑤⑥⑦ | 三个 `spawner` | 依次激活三个控制器 |

**这就是为什么必须有 launch 文件**——手动敲这 7 条命令，还要管顺序和时序，几乎不可能不出错。

**② 为什么 `robot_state_publisher` 要配 `use_sim_time: True`？**

```python
parameters=[robot_description, {'use_sim_time': True}]
```

`use_sim_time=True` 表示"**用仿真时间，不用系统时间**"。

**为什么必须开？** 仿真可以暂停、可以慢放、可以加速。如果 RViz 用墙上时钟、Gazebo 用仿真时钟，两边时间对不上，**就会出现"模型一动不动"或"轨迹瞬间冲过去"这类诡异现象**。

**规则**：**所有和仿真打交道的 ROS 节点，都要设 `use_sim_time: True`。** 忘了设是第 N 大高频问题。

**③ 为什么 spawn 是"从话题读"而不是"给文件路径"？**

```python
arguments=['-topic', 'robot_description', '-name', 'ros2_arm', ...]
```

因为 `robot_description` 已经被 ① 展开并发布了。用 `-topic` 读的一份，**和 `robot_state_publisher` 用的是完全相同的内容**，天然一致。

如果用 `-file` 各读各的（一边读 xacro、一边读 urdf），**可能出现两边模型不一致**的诡异问题。

**`-name ros2_arm` 很重要**：它决定模型在世界里的名字 `ros2_arm`，也决定了 Gazebo 内部话题的名字，比如：

```
/world/arm_world/model/ros2_arm/joint_state
```

**改了 `-name`，这些话题名全变。** 调试时用 `gz topic -l` 看到的名字就来自这里。

**④ `-r` 和 `-v4` 是什么**

| 参数 | 含义 |
|------|------|
| `-r` | **run**，启动后立即开始跑（不加就停在暂停状态，你会以为卡住了） |
| `-v4` | 日志详细度 4（0~4），4 是最详细，调试期有用 |

**新手最常见困惑**："Gazebo 打开了但什么都不动" → **十有八九是忘了 `-r`**。

**⑤ 为什么用 `TimerAction` 延迟 5 秒？**

```python
load_controllers = TimerAction(period=5.0, actions=[...])
```

**因为时序**：控制器要在 `controller_manager` 存在之后才能被加载，而 `controller_manager` 是 Gazebo 加载插件时创建的——**这需要几秒钟**。

如果不延迟，`spawner` 会报：

```
Could not contact service /controller_manager/load_controller
```

**注意**：`spawner` 自己会**重试**，所以你可能看到它报几次错然后自己好了。**这不是 bug，是正常的启动过程。**

**为什么是 5 秒？** 经验值。机器慢的话可能需要 8~10 秒。**如果一直失败，先把 5.0 改成 10.0 试试**——这是最快的验证方法。

**⑥ `IncludeLaunchDescription` 是什么**

```python
IncludeLaunchDescription(
    PythonLaunchDescriptionSource(gz_sim_launch),
    launch_arguments={...}.items(),
)
```

**"launch 文件可以嵌套 launch 文件"** —— 这里直接复用了官方 `ros_gz_sim` 包提供的 `gz_sim.launch.py`，而不是自己重写一遍启动 Gazebo 的逻辑。

**这是 ROS 2 的惯例**：**能复用官方的就复用，别自己造。** `launch_arguments` 是传给被嵌套文件的参数。

**⑦ `DeclareLaunchArgument('world', ...)` 的用处**

它让 world 文件**可以在命令行覆盖**：

```bash
ros2 launch ros2_arm_gazebo gz_launch.py world:=/路径/别的世界.sdf
```

**这种"把可变部分暴露成参数"的写法是好习惯**——测试新世界时不用改代码。同理，以后可以把 `use_gui`、`rviz` 等也做成参数。

### ⚠️ 坑（真实踩过，编号 S-2）

**两个仿真同时跑 → `/controller_manager` 撞名。**

开发时我遇到过这个现象：`spawner` 反复报错说找不到控制器、或者报"控制器已存在"，但明明配置是对的。

**原因**：之前测试用的另一个 Gazebo 还活着（进程没被回收）。**两个 `controller_manager` 都用同一个默认节点名 `/controller_manager`**，于是：

- 新仿真的 `spawner` 可能连到了**旧仿真**的 controller_manager 上；
- 旧的那个当然不认识新配置里的控制器，于是失败。

**症状特征：报错内容和你的配置对不上**，比如"控制器已存在但你从没加载过"，或者"找不到 service"却反复重试无效。

**对策**：**每次启动仿真前先清场。**

```bash

pkill -f 'ros2 launc[h]'
pkill -f 'ign gazeb[o]'
sleep 3
pgrep -af 'ign gazebo'    # 必须为空
```

**养成习惯**：启动仿真前先跑一次 `pgrep -af 'ign gazebo'`。**这是最省时间的调试前置动作。**

## 步骤 14 · 发轨迹 + 夹爪 ✅ 里程碑 ⑤

### 🎯 这一步做什么

**最终的验收**：发一条关节轨迹，看机械臂**是否真的动了**。

**为什么这一步最重要？** 因为前面所有检查都是"静态"的——控制器状态、接口归属都可以是"看起来正常"。**只有关节真的动了，才证明整条链路是通的。**

**这也是最容易骗人的一步**：控制器 active、接口 claimed、action 返回 `SUCCEEDED`，**但关节一步不动**。原因见下方 M-1。

### ⌨️ 执行（新开一个终端，仿真保持运行）

```bash
source /opt/ros/humble/setup.bash
source ~/ros2_arm/install/setup.bash

# 1. 记录动作前的关节角度
echo "--- 动作前 ---"
ros2 topic echo /joint_states --once --field position

# 2. 通过 action 发送轨迹目标（推荐用 action，不用 topic）
ros2 action send_goal /ros2_arm_controller/follow_joint_trajectory \
```

**安全取值范围**：`0.0` ~ `0.025`，实测建议用 `0.02`。

### 🔍 三个关键理解

**① 为什么用 action 而不是 topic？**

| 方式 | 特点 |
|------|------|
| `ros2 topic pub` 到 `/xxx_controller/joint_trajectory` | 发一条**消息**，**发完就没了**。如果控制器当时没准备好，消息就丢了 |
| `ros2 action send_goal` | 发一个**目标**，有**确认、反馈、结果**。控制器会告诉你"我收到了""我在执行""我完成了" |

**实测教训**：用 `topic pub --once` 发轨迹时**关节没动**——因为单次发布的消息被丢了（QoS 匹配需要时间）。改成 action 立刻成功。

**结论**：**轨迹控制一律用 action。** topic 方式只适合高频连续发布的场景。

**② `joint_names` 和 `positions` 的顺序必须对应**

```bash
joint_names: [base_joint, shoulder_joint, elbow_joint]
positions:   [0.5,          -0.4,           0.6]
              ↑ base=0.5    ↑ shoulder=-0.4 ↑ elbow=0.6
```

**这是按位置一一对应的，不是按名字去查。**

**常见错误**：把 `joint_names` 写成 `[elbow_joint, base_joint, shoulder_joint]` 但 `positions` 还是按原来的顺序给——结果机械臂动成完全不同的姿势，而且**不报错**（因为关节名都合法）。**这是最难发现的一类 bug。**

**建议**：**始终按固定顺序写**（就用本项目 yaml 里的顺序 `base → shoulder → elbow`），别每次换。

**③ 单位是弧度，不是角度**

```
0.5 rad ≈ 28.6°
-0.4 rad ≈ -22.9°
0.6 rad ≈ 34.4°
```

**想用角度就直接换算**：`角度 × 0.01745 = 弧度`。

**注意各关节限位不同**，超出会被拒绝：

| 关节 | 范围（弧度） | 约等于 |
|------|------------|--------|
| `base_joint` | -3.14159 ~ 3.14159 | ±180° |
| `shoulder_joint` | -1.5708 ~ 1.5708 | ±90° |
| `elbow_joint` | -2.0 ~ 2.0 | ±115° |
| `finger_right_joint` | -0.4 ~ 0.0 | 0° ~ -23°（闭合方向） |
| `finger_left_joint` | 0.0 ~ 0.4 | 0° ~ +23°（mimic 反向跟随） |

| 检查 | 命令 | 正常结果 |
|------|------|---------|
| 控制器是否 active | `ros2 control list_controllers` | 三个都 active |
| 接口是否 claimed | `ros2 control list_hardware_interfaces` | 4 个 `[claimed]` |

# 附录 D · 调试方法论（比记住报错更重要）

前面 20 多条坑都是**具体**的。但你以后一定会遇到表里没有的新问题。这时需要的是一套**通用的排查方法**。

## D.1 五步排错法

**这五步的顺序很重要，别跳步。**

| 步骤 | 做什么 | 为什么 |
|------|--------|--------|
| **① 定位到层** | 先判断问题在哪一层：**编译期** / **模型期** / **仿真期** / **命令期** | 四层的排查手段完全不同。胡乱试是最大的时间浪费 |
| **② 看日志文件，不看终端** | `log/latest_build/<包名>/stdout_stderr.log` | 终端只显示最后几行，真正的第一个错误往往在上面几十行 |
| **③ 缩小范围** | 一次只动一个变量 | 同时改三处，改好了也不知道是哪个起的作用 |
| **④ 找"第一个"错误** | 忽略后续的错误 | 一个错误常引发一串连锁报错。**修第一个，再看剩下的** |
| **⑤ 对照一个已知能跑的版本** | 拿原型项目和自己的文件逐行 diff | 本项目的 `docs/` 里全是**已实测通过**的代码，是最好的参照 |

**怎么快速定位到层？**

```
colcon build 报错                                    → 编译期（B 系列）
colcon 过了，但 xacro 展开失败 / check_urdf 不通过    → 模型期（M 系列）
模型没问题，但 Gazebo 起不来 / 控制器不 active        → 仿真期（S 系列）
仿真全绿但关节不动                                    → 物理层面（M-1）或命令用法（C 系列）
```

## D.2 "软件全绿但关节不动"——最值得记住的一课

这个现象在本项目里**真实发生过**（夹爪的 5 mm 间隙）。它的排查思路值得单独记住，因为**这类问题的特征非常鲜明**：

**症状**：所有"看状态"的检查都正常——

```
list_controllers          → active
list_hardware_interfaces  → [claimed]
action send_goal          → SUCCEEDED
```

**但物理上毫无反应。**

**这说明什么？** 说明**指令下发的链路是通的**——控制器收到了、认领了、返回成功了。那么问题**一定在链路末端**：指令到了电机（仿真里的关节），但推不动。

**链路末端只有三种可能：**

| 可能 | 怎么查 |
|------|--------|
| **限位太小** | 目标值是不是贴着 or 超出 `lower`/`upper`？换一个中间值做对照实验 |
| **几何干涉 / 摩擦锁死** | 算一下两个几何体的坐标，看是不是贴死了。这就是那个 5 mm 的坑 |
| **惯量异常** | 某个 link 的 `mass` 是不是 0？惯量是不是算错了一个数量级？ |

**排查动作**：绕过 ROS 层，直接看仿真器内部的真实关节值：

```bash
gz topic -l | grep joint
timeout 3 gz topic -e -t /world/arm_world/model/ros2_arm/joint_state
```

**对比"命令值"和"真实值"**：
- 命令值在变、真实值不动 → **物理卡死**（几何/摩擦/限位）；
- 命令值也不变 → 问题在**控制器侧**，回上一层查。

**"绕过中间层直接看底层的真实状态"是调试的通用技巧。** 把链路拆成几段，找到"最后一段正常的地方"和"第一段异常的地方"，问题就在两者之间。

## D.3 三个"看起来一样但完全不同"的失败

| 表面现象 | 可能的原因（差别很大） | 区分方法 |
|---------|---------------------|---------|
| "找不到文件" | 文件不存在 / 没编译 / 没 source | `ls` 看真实存在；`ros2 pkg prefix` 看 source 状态 |
| "关节不动" | 接口没声明 / 限位挡住 / 物理卡死 | 看 `list_hardware_interfaces` 的 claimed 状态；做限位对照实验 |
| "控制器加载失败" | yaml 关节名写错 / URDF 没声明接口 / 依赖没装 | 看 `log/` 里 spawner 的完整报错 |

**核心方法**：**不要根据"现象"猜原因，要主动设计实验把可能性一个个排除。**

## D.4 一个具体的实验设计示范

假设你怀疑"夹爪不动是因为几何干涉"，怎么**证明**？

❌ **不好的做法**：直接改几何，改完动了就以为找到了原因——但你改了参数同时也改了别的可能性。

✅ **好的做法**：

1. **做一个对照实验**：让活动爪的目标值分别取 `0.001`（几乎不动）、`0.01`、`0.02`（接近最大）；
2. **观察规律**：
   - 全都完全不动 → 不是"贴边卡死"，更像接口或限位问题；
   - 只有小值不动、大值能动 → 是启动时的静摩擦问题；
   - **全都完全不动，且仿真内部真实值也不变** → 强烈指向几何贴合导致的摩擦锁死；
3. **做单变量验证**：**只**改间隙（`grip_z + 0.005`），其他一律不动，重新测试；
4. **确认**：如果这一处改动就让它动了，因果链就确认了。

**这个"对照实验 → 观察规律 → 单变量验证"的流程，就是工程调试的核心。**
