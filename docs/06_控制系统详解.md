> 本章让机械臂"能动"。你会写出 2 个文件，然后看着三个控制器全部变成 `active`——

## 6.2 重点内容（一）：ros2_control 的设计思想

### 6.2.1 要解决什么问题

同一个机械臂，可能有三种"底层"：
- 在 Gazebo 里是**物理引擎**；
- 在真机上是 **PCA9685 驱动板 + I2C 总线**；
- 在测试里可能是**一个假的模拟器**（只回显指令）。

如果每个上层程序都直接对接某一种底层，换个底层就要重写所有代码。ros2_control 的做法是**插入一层统一接口**：

```
上层（控制器 / MoveIt / 你的节点）
        │  统一的接口名："把 base_joint 的位置设成 0.5 弧度"
        ▼
┌─────────────────────────────────────┐
│  ros2_control 硬件接口层（Hardware Interface）│
│  ├─ 仿真：ign_ros2_control 插件（交给物理引擎）│
│  ├─ 真机：你自己的插件（交给 I2C）           │
│  └─ 测试：mock 组件（假动作）               │
└─────────────────────────────────────┘
        │  底层细节（力矩、PWM、寄存器）
        ▼
物理引擎 / 电机驱动板
```

**这就是"接口即插槽"**：上层软件只认接口，不认底层。

### 6.2.2 三个角色的分工

| 角色 | 是什么 | 本项目里是谁 |
|------|--------|------------|
| **硬件接口 Hardware Interface** | 抽象的"电机驱动器"。负责读写每个关节的位置/速度/力矩 | 仿真：`ign_ros2_control/IgnitionSystem`；真机：你自己写（第 6.6 节） |
| **控制器 Controller** | 一段控制逻辑，消费接口、产出指令 | `ros2_arm_controller`（跟踪轨迹）、`finger_controller`（夹爪）、`joint_state_broadcaster`（只读播报） |
| **controller_manager** | 管理器：加载/配置/激活/切换控制器，提供一堆服务 | 由 Gazebo 内插件自动启动（见第 03 章） |

### 6.2.3 command interface 与 state interface（核心概念）

每个关节暴露两方向的数据通道：

```
        ┌────────────── 控制器（上层）──────────────┐
        │                                          │
   写 command_interface              读 state_interface
   "我希望你转到 0.5 rad"            "它现在实际在 0.49 rad，速度 0.02 rad/s"
        │                                          │
        ▼                                          ▲
   硬件接口（硬件/物理引擎） ──────────────────────────┘
```

| 接口 | 方向 | 谁写 | 谁读 |
|------|------|------|------|
| `command_interface`（position / velocity / effort） | 向下 | 控制器（如 ros2_arm_controller） | 硬件接口 |
| `state_interface`（position / velocity） | 向上 | 硬件接口 | 控制器、joint_state_broadcaster |

**`[claimed]` 是什么意思**：命令行 `ros2 control list_hardware_interfaces` 里，某个接口显示 `[claimed]` 表示**已经有控制器占用它**（claim = 认领）。如果某个关节的 command interface 一直是 `[unclaimed]`，说明没有任何控制器在驱动它——这个关节就不会动。

## 6.3 重点内容（二）：`ros2_arm.ros2_control.xacro`

> 写到 `src/ros2_arm_description/urdf/ros2_arm.ros2_control.xacro`

这个文件的作用是**在 URDF 里声明"每个关节暴露哪些接口、用哪个硬件插件"**。它被第 05 章的 `ros2_arm_gz.urdf.xacro` 用 `<xacro:include>` 引用。

```xml
<?xml version="1.0"?>
<!-- ============================================================
     ros2_arm.ros2_control.xacro
     作用：声明每个关节的 command / state 接口，以及底层硬件插件
     关键：插件名由调用方传入（仿真 / 真机不同），上层代码不变
     ============================================================ -->
<robot xmlns:xacro="http://www.ros.org/wiki/xacro">

  <xacro:macro name="ros2_arm_ros2_control" params="name plugin_name">

    <ros2_control name="${name}" type="system">
      <!-- 底层硬件插件：仿真时是 ign_ros2_control；真机时是你自己写的组件 -->
      <hardware>
        <plugin>${plugin_name}</plugin>
      </hardware>

      <!-- 关节 1：底座旋转 -->
      <joint name="base_joint">
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
      </joint>

      <!-- 关节 2：肩 -->
      <joint name="shoulder_joint">
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
      </joint>

      <!-- 关节 3：肘 -->
      <joint name="elbow_joint">
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
      </joint>

      <!-- 关节 4/5：夹爪两指（旋转关节，一个主动 + 一个 mimic 联动） -->
      <joint name="finger_right_joint">
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
      </joint>

      <joint name="finger_left_joint">
        <!-- 从动关节：声明跟随 finger_right_joint，倍数 -1（反向对称） -->
        <param name="mimic">finger_right_joint</param>
        <param name="multiplier">-1</param>
        <command_interface name="position"/>
        <state_interface name="position"/>
        <state_interface name="velocity"/>
      </joint>

    </ros2_control>
  </xacro:macro>

</robot>
```

**逐点说明**：

| 点 | 说明 |
|----|------|
| `type="system"` | 表示这是"一个系统"，包含多个关节。也可是 `actuator`（单关节）、`sensor`（只读传感器） |
| 为什么每个关节都要写 `position` 的 command | 本项目的关节是**位置控制**（舵机/位置伺服），不是力矩控制 |
| 为什么还要 `velocity` 的 state | 控制器用它做速度前馈、joint_state_broadcaster 用它广播；MoveIt 也需要 |
| 名字必须与 core.xacro **逐字符一致** | `base_joint` 写成 `base_jiont` → 控制器加载时报"关节不存在" |
| **不需要**在这里写夹爪的固定关节 | 固定关节不可动，没有接口 |
| `finger_left_joint` 为什么也要声明 | 它是**从动关节**，用 `<param name="mimic">` 声明跟随谁。硬件层会自动同步两个关节，**但接口必须声明出来**，否则硬件层不知道要驱动它 |

## 6.4 重点内容（三）：`ros2_arm_controllers.yaml`

> 写到 `src/ros2_arm_bringup/config/ros2_arm_controllers.yaml`

这个文件是**控制系统的"配置文件"**：声明有哪些控制器、参数是什么。它由第 05 章 gz 总装文件里的 `<parameters>` 标签喂给 `controller_manager`。

```yaml
# ============================================================
# ros2_arm_controllers.yaml
# 由 controller_manager 读取（路径写在 ros2_arm_gz.urdf.xacro 里）
# ============================================================
controller_manager:
  ros__parameters:
    update_rate: 100          # 控制频率 100 Hz（每 10 ms 下发一次指令）

    # ---- 声明三个控制器（这里只声明"有哪些"，参数在下面分开写） ----
    joint_state_broadcaster:
      type: joint_state_broadcaster/JointStateBroadcaster

    ros2_arm_controller:
      type: joint_trajectory_controller/JointTrajectoryController

    finger_controller:
      type: position_controllers/GripperActionController

# ---- 控制器 1：机械臂轨迹控制器 ----
ros2_arm_controller:
  ros__parameters:
    joints:                   # 顺序可以任意，但名字必须与 URDF 完全一致
      - base_joint
      - shoulder_joint
      - elbow_joint
    command_interfaces:
      - position
    state_interfaces:
      - position
      - velocity
    allow_nonzero_velocity_at_trajectory_end: false   # 轨迹终点速度归零，避免抖动

# ---- 控制器 2：夹爪（只控主动指，从动指由 mimic 自动跟随）----
finger_controller:
  ros__parameters:
    joint: finger_right_joint
```

### 6.4.1 三个控制器各自是什么

| 控制器 | 类型 | 作用 | 关键参数 |
|--------|------|------|---------|
| `joint_state_broadcaster` | `JointStateBroadcaster` | **只读**：把各关节实际状态汇总发布到 `/joint_states` | 无（自动覆盖所有有 state 接口的关节） |
| `ros2_arm_controller` | `JointTrajectoryController` | 接收**轨迹**（每个关节随时间的角度序列），按周期插值下发 | `joints`、`command_interfaces` |
| `finger_controller` | `GripperActionController` | 接收**夹爪目标**（张开/闭合位置），自带"到位判定" | `joint` |

**`update_rate: 100` 的含义**：控制器每秒下发 100 次指令。太低（如 10 Hz）动作会一顿一顿；太高可能超过物理引擎能力（本机实测会有个"update period 比仿真周期慢"的警告，属正常提示，不影响功能）。

**`allow_nonzero_velocity_at_trajectory_end`**：轨迹结束时允许非零速度。设 `false` 更稳（到点停住）。原型项目设的 `true`，会有一条"已废弃"的黄色告警——**本项目直接设 false，干净利落**。

### 6.4.2 名字三处必须一致（本书最重要的检查项）

```
ros2_arm_core.xacro        里的 <joint name="shoulder_joint">
ros2_arm.ros2_control.xacro 里的 <joint name="shoulder_joint">
ros2_arm_controllers.yaml   里的 joints: - shoulder_joint
```

**三处逐字符一致**，少一个字母，控制器就激活不了。写完后用这条命令快速核对（它就是干这个用的）：

```bash
grep -o 'name="[a-z_]*_joint"' src/ros2_arm_description/urdf/ros2_arm_core.xacro | sort -u
grep -o 'name="[a-z_]*_joint"' src/ros2_arm_description/urdf/ros2_arm.ros2_control.xacro | sort -u
grep -E '^\s+-?\s*[a-z_]*_joint' src/ros2_arm_bringup/config/ros2_arm_controllers.yaml
```

## 6.5 重点内容（四）：验收控制系统

### 6.5.1 前提：第 05、06、07 章配合启动

控制器要靠 Gazebo 里的插件才能诞生，所以**必须第 07 章的 launch 就绪后**才能验收本章。第 07 章会给你 `gz_launch.py`，它负责：起 Gazebo → 加载机械臂 → **依次激活 3 个控制器**。

顺序参考（第 07 章详解）：

```bash
cd ~/ros2_arm && colcon build --symlink-install && source install/setup.bash
ros2 launch ros2_arm_gazebo gz_launch.py
```

### 6.5.2 四条验收命令

```bash
source /opt/ros/humble/setup.bash
source ~/ros2_arm/install/setup.bash

# ① 三个控制器都在，且状态是 active
ros2 control list_controllers

# ② 每个关节的 command interface 都是 [claimed]
ros2 control list_hardware_interfaces

# ③ 关节状态在广播
ros2 topic echo /joint_states --once --field position

# ④ controller_manager 真的存在（它由 Gazebo 插件创建）
ros2 node list | grep controller_manager
```

**① 的期望输出**：

```
joint_state_broadcaster joint_state_broadcaster/JointStateBroadcaster          active
finger_controller       position_controllers/GripperActionController           active
ros2_arm_controller     joint_trajectory_controller/JointTrajectoryController  active
```

**② 的期望输出（关键看 `[claimed]`）**：

```
command interfaces
	base_joint/position [available] [claimed]
	elbow_joint/position [available] [claimed]
	finger_left_joint_mimic/position [available] [unclaimed]
	finger_right_joint/position [available] [claimed]
	shoulder_joint/position [available] [claimed]
state interfaces
	base_joint/position
	base_joint/velocity
	...
```

> **两条判据都绿才算控制系统就绪。** 只有控制器 `active` 但接口没 `[claimed]`，说明硬件插件没接上——机械臂不会动。

### 6.5.3 最有力的验收：发一条轨迹，看它真的动

用 **action** 方式（比往话题里 pub 更可靠，原因见 6.5.4）：

```bash
# 记下动作前的关节角度
ros2 topic echo /joint_states --once --field position

# 发一条 4 秒的轨迹目标：底座 0.5 rad、肩 -0.4 rad、肘 0.6 rad
ros2 action send_goal /ros2_arm_controller/follow_joint_trajectory \
  control_msgs/action/FollowJointTrajectory \
  "{trajectory: {joint_names: [base_joint, shoulder_joint, elbow_joint],
    points: [{positions: [0.5, -0.4, 0.6], time_from_start: {sec: 4}}]}}"

# 执行中/结束后再看一次关节角度，应当朝目标值变化
ros2 topic echo /joint_states --once --field position
```

**期望看到**：终端输出 `Goal finished with status: SUCCEEDED`，且 `/joint_states` 的值明显朝 `[0.5, -0.4, 0.6]` 靠近。同时 Gazebo 窗口里机械臂真的转过去了。

夹爪测试（先张开后闭合）：

```bash
ros2 action send_goal /finger_controller/gripper_cmd \
  control_msgs/action/GripperCommand "{command: {position: 0.0, max_effort: 10.0}}"    # 张开（指竖直）
ros2 action send_goal /finger_controller/gripper_cmd \
  control_msgs/action/GripperCommand "{command: {position: -0.4, max_effort: 10.0}}"   # 闭合
```

### 6.5.4 一个实测踩到的坑：`ros2 topic pub` 会丢消息

`ros2_arm_controller` 的轨迹话题订阅 QoS 是 **BEST_EFFORT**（尽力而为、不重传），而 `ros2 topic pub --once` 只发一条、发完就退出，很可能在 DDS 完成"发现匹配"之前就把消息丢了——**表现为"发了没反应"**。

**对策（按推荐度排序）**：
1. 用 action（`ros2 action send_goal`）—— 最可靠，还能看到 `SUCCEEDED`；
2. 或连续发多条：`ros2 topic pub -r 2 <话题> <类型> '<内容>'`，发 5 秒以上（Ctrl+C 结束）。

## 6.6 重点内容（五）：从仿真到真机（认知即可，不必动手）

真机需要你自己实现一个硬件组件，本质是继承 ros2_control 的 `SystemInterface` 并填 6 个函数：

| 函数 | 你要在里面做什么 |
|------|----------------|
| `on_init` | 读参数（I2C 地址、关节数） |
| `on_configure` | 建立接口清单（哪些关节、哪些 command/state） |
| `on_activate` | 打开 I2C 设备、复位舵机 |
| `read` | 从舵机/编码器读回实际角度 → 写进 state interface |
| `write` | 从 command interface 取出目标角度 → 换算成 PWM → 通过 I2C 下发 |
| `on_deactivate` | 安全停机（松开舵机） |

原型 akabot 的 `akabot_bringup/src/pca9685_system.cpp` 就是这样一个实现，你可以去读它的结构（**不要试图读懂每个寄存器**，先看它实现了哪些函数、函数名和上面这张表怎么对应）。

**切换方式**：把 `ros2_arm_gz.urdf.xacro` 里的

```xml
<xacro:ros2_arm_ros2_control name="Ros2ArmSystem" plugin_name="ign_ros2_control/IgnitionSystem"/>
```

改成你自己的插件名（例如 `ros2_arm_bringup/Ros2ArmHardware`），**上层所有软件、配置、MoveIt 全部不动**。这就是第 03 章讲的"对称性"。

## 6.7 常见错误速查表

| 报错 / 现象 | 原因 | 解决 |
|-----------|------|------|
| `Could not contact service /controller_manager/list_controllers` 反复刷 | 控制器加载器在等 `controller_manager`——**Gazebo 还没起或顺序错了** | 先起 Gazebo，等它加载完插件，controller_manager 才存在 |
| `Controller already loaded, skipping load_controller` + `Failed to configure controller`，且 spawner 退出码 1 | **正常现象**：控制器已经 active，不能重复 configure | 忽略；想干净重来就重启 Gazebo（spawner 不幂等） |
| 控制器状态是 `inactive` / `unconfigured` | 关节名对不上，或接口类型不匹配 | 用 6.4.2 的三条 grep 核对名字 |
| `list_hardware_interfaces` 里没有我的关节 | `ros2_control.xacro` 没被 include，或没被 `<xacro:..._ros2_control/>` 调用 | 检查 gz 总装文件的两处引用 |
| 机械臂能激活控制器但**不动** | command interface 未 `[claimed]`，或轨迹只发了一条被丢了 | 看 `list_hardware_interfaces`；改用 action |
| 某个关节**恒为 0、发指令毫无反应**，而其他关节正常 | **物理原因**：该关节的活动件与固定件几何贴合，被接触摩擦卡住 | 见第 05 章 5.8.1 的实战案例（留 2~5 mm 间隙） |
| 夹爪 `GripperCommand` 返回 `ABORTED` 且 `reached_goal: false` | ①几何卡住；②用的是平移关节、机械臂一倾斜就被重力顶住（详见 05 章 5.8.1）；③目标值贴着限位边界 | 夹爪用 `revolute` + `mimic`；目标值别贴边界下发 |
| `finger_left_joint_mimic/position` 显示 `[unclaimed]` | **正常现象** | 从动关节由硬件层自动跟随，本来就不该被控制器认领 |
| `Desired controller update period (0.01 s) is slower than the gazebo simulation period` | 控制频率低于物理步长，只是提示 | 忽略，或把 `update_rate` 提到 1000（一般不必） |
| WARN `The ign_ros2_control plugin got renamed to gz_ros2_control` | 上游改名，旧名仍兼容 | 忽略（本项目用的是实测可用的旧名） |
